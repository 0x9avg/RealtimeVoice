# RealtimeVoice

Голосовой ИИ-контур для роботов Unitree R1 (презентатор у видеостены) и G1 (помощник поста охраны): браузер
или аппаратный микрофон робота захватывает речь и текстовый ввод, FastAPI backend держит сессию Gemini Live
API (аудио-в/аудио-из, с tool calling) и отдаёт аудио-ответ обратно — в браузер или на динамик робота. Один
и тот же код обслуживает обе роли — разными профилями (`ROBOT_PROFILE=r1`/`g1`), см. раздел «Профили».

Для деплоя, запуска и настройки на роботе — `DEPLOYMENT.md`. Этот файл — архитектура и объяснение инженерных
решений: зачем сделано именно так, что откуда переиспользовано, что проверять при изменениях.

Зачем именно так и что из этого переиспользовано из соседнего репозитория — см. `../CLAUDE.md`. Протокол
общения с Gemini Live (WS-URL, формат `setup`/`realtimeInput`/`clientContent`/`toolCall`/`toolResponse`)
переиспользован из уже проверенной в бою реализации в
`../../humanoid-robot/packages/humanoid-robot-adapters-live-gemini/`, а не написан с нуля.

## Архитектура

```
Browser #1 ─┐                              FastAPI backend (app/)                Gemini Live API
Browser #2 ─┼─ /ws/session (WS) ──▶  app/session_hub.py: SessionHub  ──send_audio──▶  GeminiLiveAdapter ──▶ BidiGenerateContent
Browser #N ─┘                        (ОДНА на весь процесс,          ◀──audio/toolCall/turn───────────────
            ◀── broadcast всем ──    живёт с запуска сервера,
                подписчикам          не привязана к соединению)
                                              ToolRegistry.dispatch() ──▶ get_current_time / …
```

**Одна сессия на процесс, не на соединение.** `SessionHub` — единственный экземпляр `GeminiLiveAdapter` +
набор инструментов + (если включено) реальные микрофон/динамик робота, создаётся один раз при старте сервера
(`app/main.py`'s lifespan) и живёт независимо от того, сколько браузеров сейчас подключено — хоть ноль, хоть
несколько. `/ws/session` — это просто подписка на неё: `SessionHub.join()` регистрирует сокет, шлёт ему
текущие `capabilities` и реплеит недавнюю историю (транскрипт/tool-события, до 300 последних сообщений) —
поэтому вкладка, открытая позже остальных, видит ТУ ЖЕ страницу, а не пустой транскрипт. Любое управляющее
действие (текст, `mic_source`, `mute`) от любой вкладки действует на общую сессию; `SessionHub.leave()` при
отключении просто убирает сокет из списка подписчиков — сама сессия, микрофон и разговор с Gemini продолжают
работать для всех остальных (и для самого робота, даже если ни одна вкладка не открыта). До этого изменения
каждое WS-соединение поднимало СВОЙ `GeminiLiveAdapter`+`RobotSpeaker`+`RobotMic` — две открытые вкладки означали
два независимых разговора и попытку одновременно рулить одним и тем же физическим микрофоном/динамиком.

Ресемплинг делает сам браузер: `AudioContext` для захвата создаётся с `sampleRate: 16000`, для воспроизведения —
с `sampleRate: 24000`, поэтому на backend нет никакой обработки аудио, только пересылка байтов.

Непрерывный разговор без push-to-talk: пока микрофон включён, аудио стримится постоянно, конец хода определяет
серверный VAD самой Gemini Live. Barge-in: событие `interrupted` от Gemini backend пересылает в браузер как
`{"type":"interrupted"}`, а тот сразу останавливает и очищает очередь воспроизведения.

## Быстрый запуск для разработки

Полная процедура для реального робота — в `DEPLOYMENT.md`. Здесь — минимум для локальной работы над кодом:

1. Скопируйте `.env.r1.example` (или `.env.g1.example`) в `.env` и впишите свой `GEMINI_API_KEY` (ключ Google
   AI Studio с доступом к Gemini Live API).
2. Установите зависимости и запустите сервер:

   ```bash
   uv sync
   uv run uvicorn app.main:app --reload
   ```

3. Откройте `http://localhost:8000` в Chrome или Edge (нужны `getUserMedia` и `AudioWorklet`).

## Видеостена (`control_video_wall`)

Голосовой backend никогда не трогает MinTrans/Factories.exe напрямую — он говорит по HTTP с отдельным
процессом-агентом (`app/wall/`, `WALL_AGENT_URL` в `.env`), а тот уже знает, как управлять приложением. Это
разделение и есть то, что делает решение сетевым: backend и агент видеостены могут стоять на разных машинах.

Запуск агента — отдельным процессом, с выбором драйвера:

```bash
uv run python -m app.wall --driver sim --port 8093     # симулятор — любая ОС, для разработки
uv run python -m app.wall --driver pipe --port 8093     # реальный Factories.exe — только Windows
```

- **`sim`** — модель приложения в памяти (тот же процесс, что использовался при разработке этого прототипа).
  Ничего не требует, работает где угодно, ничего реально не переключает.
- **`pipe`** — управляет настоящим Factories.exe через его собственный именованный пайп
  (`S.Networks.Pipes.Unity.MinTrans`), реверс-инжинирнутый из `Assembly-CSharp.dll` и подтверждённый вживую
  (02.09.2026: `MENU_AERO1`/`MENU_JD2` реально переключили сцену, со скриншотами). Работает только если **сам
  процесс агента** запущен на Windows — это не WSL-хак: обычный `open(r"\\.\pipe\...")` в Python, потому что
  именованные пайпы принципиально локальны для машины. На Linux/WSL `--driver pipe` сразу и честно откажет с
  понятной ошибкой вместо того, чтобы притворяться рабочим.

Чтобы голос реально управлял стеной: разверните `app/wall` на Windows-ПК стены рядом с Factories.exe
(`uv run python -m app.wall --driver pipe`, или см. ниже — готовый `wall-agent.exe`, если на этом ПК не хочется
ставить Python), а в `.env` голосового backend'а (который может работать на любой другой машине в той же сети)
укажите `WALL_AGENT_URL=http://<адрес-пк-стены>:8093`. Код `control_video_wall` (`app/tools.py`) не меняется —
он всегда просто обращается к `WALL_AGENT_URL`, независимо от того, что за драйвер и где физически стоит агент.

### Видеостена — установка на Windows без Python (`wall-agent.exe`)

ПК видеостены обычно принадлежит контрагенту, который поставил Factories.exe, и ставить туда Python/uv вручную
неудобно каждый раз. `scripts/build_wall_agent_windows.bat` собирает `app/wall` в один файл `wall-agent.exe`
через [PyInstaller](https://pyinstaller.org/) — дальше на ПК стены нужен только этот файл, ни Python, ни uv,
ни `pip install` там не требуются вообще.

**Сборка exe — один раз, на ЛЮБОЙ Windows-машине с [uv](https://docs.astral.sh/uv/)** (не обязательно на самом
ПК стены — например, на ноутбуке разработчика):

```bat
scripts\build_wall_agent_windows.bat
```

Результат — `dist\wall-agent.exe` (один файл, ничего больше не нужно копировать для запуска). Пересобирайте
после любых изменений в `app/wall/`.

**На самом ПК стены** — скопируйте `dist\wall-agent.exe` и, для удобства, `scripts\run_wall_agent.bat` (запускает
exe с `--driver pipe --port 8093` без необходимости каждый раз набирать команду в консоли — впишите
`WALL_AGENT_TOKEN` в начале файла, если нужен `X-Wall-Token`) в одну папку рядом с Factories.exe. Дальше — просто
двойной клик по `run_wall_agent.bat` (или по самому `wall-agent.exe`, если параметры по умолчанию устраивают).
Для автозапуска при включении ПК — обычный ярлык на `run_wall_agent.bat` в `shell:startup`; отдельного механизма
автозапуска (Task Scheduler и т.п.) этот прототип не настраивает, только сам exe/bat.

Это **не** установщик самого Factories.exe или Windows-агента для звука/видеостены как системной службы —
только удобная сборка `app/wall` без ручной установки Python на машину, где он итак не нужен ни для чего
другого. Один и тот же exe работает независимо от того, какая машина в сети слушает `WALL_AGENT_URL` —
топология из абзаца выше не меняется.

Известные ограничения реального приложения (подтверждены реверс-инжинирингом `level0`, не выдуманы):
раздел `Avto5` не имеет pipe-команды вообще, `open_section` для него корректно отклоняется. Пошаговое
переключение разделов и слайдов вперёд/назад (`next_section`/`prev_section`/`next_slide`/`prev_slide`)
**не реализовано нигде** — ни в `WallNavAction` (`app/wall/commands.py`), ни в драйверах, ни в инструменте ИИ,
ни на странице «Видеостена»: в реальном приложении для этого нет ни одной pipe-команды (слайды слушают только
PgUp/PgDn напрямую), и сами разделы внутри категории не имеют содержательного порядка, чтобы «следующий»/
«предыдущий» вообще что-то значили. Остаётся только открыть конкретный раздел/категорию по имени —
`open_section`/`open_category` — и `navigate` с единственным действием `main_menu`.

## Запуск на роботе (реальный микрофон/динамик через `unitree_sdk2py`)

`app/robot_audio.py`'s `RobotSpeaker` требует нативный вендорский SDK (`unitree_sdk2py` + CycloneDDS с
поддержкой iceoryx/shared-memory). На этом роботе на диске есть **две разные сборки CycloneDDS**, и от того,
какую из них реально загрузит процесс, зависит, заработает вывод звука через колонку робота или упадёт
сегфолтом:

- `/usr/local` — вендорская сборка, идёт в паре с демоном `/usr/local/bin/iox-roudi` (нужен и ему, и всей
  остальной робото-платформе). **Несовместима** с python-пакетом `cyclonedds`, поставленным обычным
  `uv pip install cyclonedds` — падает сегфолтом внутри `iox_pub_publish_chunk` на первом же RPC-вызове
  (`AudioClient.SetVolume`/`Init`), даже если `iox-roudi` запущен и сконфигурирован правильно. Это не баг
  этого прототипа и не баг конкретной версии python-пакета — несовпадение ABI между тем, как каждая из сборок
  трактует внутренние структуры CycloneDDS при передаче данных через iceoryx.
- `~/cyclonedds_ws/install/cyclonedds` — отдельная сборка CycloneDDS из исходников (colcon/ROS2-стиль), собрана
  именно по инструкции самого `unitree_sdk2_python` (`CYCLONEDDS_HOME` перед `pip install cyclonedds`, а не
  просто `pip install cyclonedds` вслепую). **С этой сборкой всё работает.**

Поэтому перед запуском с `AUDIO_OUTPUT=robot` (или `AUDIO_INPUT=robot`, хотя вход не использует DDS вообще —
только UDP-мультикаст, ему это не нужно) обязательно экспортировать:

```bash
export LD_LIBRARY_PATH=/home/unitree/cyclonedds_ws/install/cyclonedds/lib:$LD_LIBRARY_PATH
export CYCLONEDDS_URI=/home/unitree/cyclonedds_ws/cyclonedds.xml
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
# или headless: uv run python -m app.robot_main
```

**Не полагайтесь на `.bashrc`** — там `LD_LIBRARY_PATH` указывает на `/usr/local` (нужно остальной
робо-платформе), а не на `cyclonedds_ws`, и `.bashrc` в любом случае не подхватывается неинтерактивными
SSH-командами (`ssh host 'command'`) — только явный `export` в самой команде запуска. Если после
`uv sync`/переустановки зависимостей звук на роботе снова начал падать сегфолтом — почти наверняка `cyclonedds`
пересобрался/переустановился без этого `LD_LIBRARY_PATH` и слинковался не с той библиотекой; переустановка
самого пакета не нужна, достаточно правильного `LD_LIBRARY_PATH` при запуске.

### Внешний USB-микрофон (третий вариант входа, независимый от `AUDIO_INPUT`)

Помимо головного массива микрофонов (`AUDIO_INPUT=robot`, DDS/мультикаст, см. выше) и микрофона браузера,
`app/robot_audio.py`'s `UsbMic` умеет читать **любой обычный USB-микрофон, подключённый к бортовому компьютеру
робота напрямую** — ALSA видит его как обычную звуковую карту, вендорский SDK тут не нужен вообще. Проверено
вживую на этом R1 (04.09.2026): конференц-микрофон Jabra Speak2 40 MS определился как `card 2 [MS]` (`arecord
-l`/`cat /proc/asound/cards`), запись `arecord -D hw:MS,0 -f S16_LE -r 16000 -c 1` даёт настоящий (не тишина —
замеренный RMS/max на образце в 2с подтвердил реальный сигнал) моно PCM16 16кГц — тот же формат, что Gemini Live
ждёт на входе, ресемплинг не нужен.

Включается независимо от `AUDIO_INPUT` одной переменной:

```bash
USB_MIC_ALSA_DEVICE=hw:MS,0   # ALSA-ID карты, НЕ числовой индекс — см. .env.*.example
```

С этим заданным на сайте («Главная») в выпадающем списке источника микрофона появляется третий пункт —
«Внешний (USB)», рядом с «Микрофон браузера» и «Встроенный (робот)». Как и микрофон робота, это **глобальный
переключатель** (`app/robot_mic_state.py`, теперь общий для обоих аппаратных источников, не только головного
массива) — состояние видно всем открытым вкладкам, и **только один аппаратный источник может быть активен
одновременно** (переключение на «Внешний (USB)» автоматически снимает «Встроенный (робот)», и наоборот — оба
пишут в один и тот же физический динамик/`HalfDuplexGate`, одновременная подача с двух источников только
задвоила бы то, что слышит Gemini).

Реализовано через субпроцесс `arecord` (`alsa-utils`, уже стоит на роботе), а не через Python ALSA/PortAudio
биндинг — не требует новой зависимости в `pyproject.toml`. Если конкретное устройство пропадёт (отключили USB)
— `UsbMic.stream()` завершится штатно (лог `usb_mic.arecord_exited`), процесс не упадёт; чтобы отдать голос
снова, надо переключить источник обратно на «Микрофон браузера»/«Встроенный (робот)» на сайте.

### Камера и реакция на посетителя (`app/robot_camera.py`, `app/camera_hub.py`, `app/presence.py`)

Камера G1 физически висит на другом бортовом компьютере, не на Jetson — здесь нет `/dev/video*` вообще
(проверено: `lsusb`, `lsmod`, нет `uvcvideo`). Доступ — через `unitree_sdk2py.go2.video.video_client.VideoClient`
поверх DDS (тот же `go2`-неймспейс, что и с `g1_audio_client` — Unitree не сделал отдельного видео-модуля для
G1), тот же класс DDS RPC-клиента, что и `AudioClient`, и требует **тот же фикс**, что и звук:

```bash
export LD_LIBRARY_PATH=/home/unitree/cyclonedds_ws/install/cyclonedds/lib:$LD_LIBRARY_PATH
export CYCLONEDDS_URI=/home/unitree/cyclonedds_ws/cyclonedds.xml
```

**Проверено вживую на роботе** (03.09.2026): `VideoClient.GetImageSample()` с этим окружением не падает и
отдаёт реальный JPEG 1280×720. **Важно**: это широкоугольный (рыбий глаз) вид **вниз**, на пол и ближайшие
предметы — похоже, это утилитарная/навигационная камера (`go2`-неймспейс — вероятно, камера квадропеда для
объезда препятствий), а не «глаза» на уровне человека. Годится, чтобы увидеть, что происходит рядом с
роботом, но для «замечает подходящего издалека посетителя» может не подойти — это открытый вопрос к
железу/установке, не к коду.

`app/camera_hub.py`'s `CameraHub` — единственный опрос DDS на процесс (по образцу `FrameHub` из
`../../humanoid-robot`'s `camera_mjpeg.py`): и просмотр на сайте, и детекция присутствия читают из одного и
того же опроса, а не заводят по своему клиенту каждый — иначе два независимых опроса одного DDS-сервиса.

**Просмотр камеры на сайте**: `GET /api/camera/snapshot` (один кадр) и `GET /api/camera/stream` (MJPEG,
`multipart/x-mixed-replace` — то, что рендерит `<img>` на странице «Главная», `components/CameraView.tsx`)
работают **независимо от `PRESENCE_ENABLED`** — хаб стартует лениво при первом запросе. Токен (если задан
`ACCESS_TOKEN`) передаётся `?token=`, т.к. `<img>` не может выставить заголовок — тот же приём, что и в
`humanoid-robot`'s камера-мосте.

**Автоприветствие**: как только `MotionDetector` (покадровое вычитание в градациях серого, без ML —
перенесено из `../../humanoid-robot/apps/presence`) фиксирует устойчивое движение, в активную голосовую сессию
уходит `adapter.send_text(PRESENCE_MARKER)` — модель сама, по системной инструкции (`app/scenarios.py`),
естественно здоровается в характере своего профиля. Выключено по умолчанию (`PRESENCE_ENABLED=false`) — сам
доступ к камере проверен, а вот полный путь «движение → голосовое приветствие» вживую ещё не прогонялся, плюс
открыт вопрос по углу обзора выше.

```bash
export PRESENCE_ENABLED=true
uv run python -m app.robot_main   # или app.main через браузер
```

Настройки: `PRESENCE_CAMERA_IFACE` (по умолчанию `eth10`), `PRESENCE_THRESHOLD` (`0.02`), `PRESENCE_REARM_S`
(`60.0`), `PRESENCE_FPS` (`2.0`, темп опроса самим детектором) и `PRESENCE_CAMERA_FPS` (`8.0`, темп опроса
хабом — от него зависит плавность картинки на сайте). `MotionDetector`/`PresenceRunner` проверены юнит-тестом
на синтетических кадрах (без камеры).

С появлением `app/session_hub.py` (одна сессия на процесс, живёт с момента старта сервера — см. «Архитектура»
выше) `app.main` тоже слушает/говорит автономно, без открытого браузера — разница между `app.robot_main` и
`app.main` теперь только в том, нужен ли вам сайт (транскрипт, кнопки, камера в браузере) поверх той же логики,
а не «автономно или только через браузер», как было раньше.

## Продакшн-развёртывание (автозапуск, Wi-Fi, защита API)

Пошаговые процедуры — в `DEPLOYMENT.md`. Здесь — инженерные решения, стоящие за ними.

**Автозапуск** — `deploy/realtimevoice-{r1,g1}.service`, юниты **пользовательского** systemd
(`~/.config/systemd/user/`, не `/etc/systemd/system/`). Намеренный выбор: не требует root/sudo вообще, в
отличие от системного systemd — актуально, если у пользователя, от которого работает сервис, нет
passwordless sudo. `Restart=on-failure` — если процесс упадёт (в т.ч. зависнет в блокирующем DDS-вызове и
получит `kill -9`) — systemd поднимет его заново сам, без ручного вмешательства через SSH.

Дополнительная сеть надёжности внутри самого процесса: `app/session_hub.py`'s фоновые задачи
(`_pump_gemini`/`_robot_mic_task`/`_presence_task`) обёрнуты в супервизор — если какая-то из них всё же упадёт
необработанным исключением, процесс сам завершится (`os._exit`), и systemd поднимет чистый заново — вместо
«сайт вроде отвечает, а робот навсегда замолчал» (процесс жив, но один из фоновых циклов молча умер — снаружи
неотличимо от нормальной работы, пока кто-то не заговорит с роботом и не получит тишину).

**Wi-Fi**: NetworkManager с `autoconnect=yes`, `autoconnect-retries=-1` (бесконечные повторные попытки) — уже
устойчиво к обрывам связи само по себе. Отдельно стоит отключить энергосбережение Wi-Fi-адаптера
(`wifi.powersave`) — штатное поведение Ubuntu держит его включённым, что периодически просаживает связь именно
под непрерывной нагрузкой вроде голосового стриминга.

**Защита API** — `/ws/session` раньше не проверял вообще ничего: любое устройство в той же сети могло
подключиться к сокету напрямую (в обход сайта) и управлять активным разговором — заглушить робота, выдать
себя за текст-ввод, дёрнуть видеостену. Теперь `/ws/session` требует тот же `ACCESS_TOKEN`, что и REST-эндпоинты
(`app/auth.py`) — через `?token=`, т.к. браузерный WebSocket не может выставить заголовок; сравнение —
`hmac.compare_digest`, не `==`, чтобы не давать угадывать токен по времени ответа. **Голосового взаимодействия
с самим роботом (микрофон/динамик) это не касается** — оно не идёт через `/ws/session` вообще, посетитель у
стойки токен не вводит. Токен нужен только для веб-интерфейса (сайт-наблюдатель/пульт оператора, `/wall`,
`/guard`) — без него сайт покажет форму запроса токена и не даст ничего увидеть/сделать. При пустом
`ACCESS_TOKEN` (значение по умолчанию) проверка полностью отключена — подходит только для изолированной сети.

## Технические заметки и объём текущей поставки

- **Модель Gemini Live** — по умолчанию `models/gemini-3.1-flash-live-preview`. Список доступных Live-моделей
  завязан на конкретный API-ключ/аккаунт; если подключение сразу падает с ошибкой — задайте `GEMINI_LIVE_MODEL`
  в `.env` на модель, реально доступную вашему ключу.
- **Аудио-путь** — по умолчанию звук идёт через браузер (`AUDIO_OUTPUT`/`AUDIO_INPUT=browser`): backend не
  трогает аудио-устройства напрямую, ресемплинг делает сам `AudioContext` в браузере. Для реального робота
  есть отдельный путь через аппаратный микрофон/динамик (`=robot`, поверх `unitree_sdk2py`/DDS) — см. раздел
  «Запуск на роботе».
- **Наблюдаемость** — сегодня это структурированные логи через `journalctl`/stdout (см. `DEPLOYMENT.md`,
  раздел «Управление сервисом»); отдельного JSONL event log или агрегированных p50/p95-метрик задержки нет.
  Для текущего объёма поставки (два независимых деплоя, один оператор на каждый) логов достаточно для
  диагностики; централизованный мониторинг — кандидат на следующий этап, если появится несколько объектов
  под одним наблюдением.
- **Проверка корректности** — сам голосовой контур (STT/TTS/tool-calling против реального Gemini Live API)
  проверяется только вживую — это в принципе не автоматизировать без реального API-ключа и живой модели, и
  ручной чек-лист ниже как раз для этого. Детерминированная логика без внешнего API — `app/visit_intake.py`
  (визит-интервью на двух языках, включая обязательный сброс на «нет»), `app/presence.py`'s `MotionDetector`,
  `app/session_hub.py`'s подписка/broadcast/история, `/ws/session`'s проверка токена, устойчивость к сбоям
  фоновых задач — покрыта тестами в `tests/`, запускаются `uv run pytest`.

## Ручной чек-лист

1. Нажать **Start mic**, разрешить доступ к микрофону, сказать что-нибудь — статус должен перейти
   `listening → speaking`, должен идти звук ответа, в транскрипте — реплики.
2. Ввести вопрос текстом и нажать **Send** — должен прийти голосовой ответ без использования микрофона.
3. Спросить "который час?" / "what time is it?" — в логе tool calls должен появиться вызов `get_current_time`,
   а озвученный ответ — содержать корректное текущее время.
4. Заговорить во время проигрывания ответа (barge-in) — воспроизведение должно оборваться быстро, а не
   доиграть до конца.
5. Нажать **Замолчи** во время ответа — воспроизведение должно остановиться мгновенно.

## Профили (R1/G1), guardrail'ы и G1-инструменты

Один и тот же код обслуживает обе роли через `ROBOT_PROFILE` (`r1` по умолчанию, или `g1`) — см.
`app/config.py`, `app/scenarios.py` (тематический и языковой system_instruction), `app/tool_registry.py`
(какие инструменты регистрируются на каком профиле). `Settings` — синглтон, читается один раз при импорте,
поэтому смена профиля — это переменная окружения + перезапуск процесса, без горячего переключения.

6. **Переключение профиля**: `ROBOT_PROFILE=r1` (по умолчанию) → запустить сервер → в логах строка вида
   `session.start profile=r1 tools=[...]` с `control_video_wall`/`search_knowledge`, без `visit_intake`/
   `search_guard_kb`. Поставить `ROBOT_PROFILE=g1` → перезапустить → обратная картина. Панель tool-call
   лога в браузере (фронтенд не менялся) должна показывать только инструменты активного профиля при их
   вызове.
7. **Тематический отказ (оба профиля)**: вопрос вне разрешённой темы (например «какая погода в Алматы?»
   на r1, что-то не про визит и не про консультации на g1) → вежливый отказ с переадресацией к
   сотруднику/охраннику, без выдумывания ответа.
8. **Языковой отказ**: вопрос на языке, отличном от русского/казахского/английского (например по-французски
   или по-немецки) → робот вежливо отказывается отвечать на этом языке, объясняет по-русски, что
   поддерживает русский, казахский и английский, и НЕ замолкает и не зависает. Отдельно проверить, что
   вопрос по-английски (например "What time is it?") — теперь разрешённый язык — отрабатывает нормально и
   НЕ попадает под этот отказ, как и вопрос по-казахски.
9. **Полный happy path визита (профиль g1)**: сказать «оформите визит» → на вопрос о языке ответить «на
   русском» → ответить по порядку на все 6 вопросов (ФИО → организация → цель → к кому → пропуск да/нет →
   удостоверение да/нет) → на зачитанную карточку ответить «да». Проверить: (а) озвучка на каждом шаге
   близка к тому, что вернул инструмент `visit_intake` (по логу tool-call в браузере и по отсутствию
   `relay_divergence`-warning в логах сервера), (б) в `data/visits.jsonl` появилась новая строка с
   корректными полями, включая `"language": "ru"`.
10. **Тот же сценарий на казахском**: сказать «оформите визит», на вопрос о языке ответить «қазақша» —
    все следующие вопросы и финальное зачитывание карточки должны идти по-казахски (ФИО-вопрос начинается
    с «Тегіңізді...»). Завершить визит («иә» на подтверждении) — в `data/visits.jsonl` должна появиться
    запись с `"language": "kk"`.
11. **Тот же сценарий на английском**: сказать «оформите визит», на вопрос о языке ответить «English» —
    все следующие вопросы и финальное зачитывание карточки должны идти по-английски (ФИО-вопрос —
    "Please tell me your full name."). Завершить визит («yes» на подтверждении) — в `data/visits.jsonl`
    должна появиться запись с `"language": "en"`.
12. **«Нет»/«жоқ»/«no» на подтверждении обязательно перезапускает интервью с нуля** — самое хрупкое правило
    здесь, и оно должно работать во ВСЕХ ТРЁХ языках. Пройти все 6 вопросов, на «Всё верно?»/«Бәрі дұрыс
    па?»/«Is that correct?» ответить «нет»/«жоқ»/«no» — следующий вопрос робота должен быть ПЕРВЫМ (ФИО)
    заново, на том же языке, а не точечным уточнением одного поля. Пройти интервью повторно до конца и
    подтвердить «да»/«иә»/«yes» — только тогда должна появиться запись в `data/visits.jsonl`. Любая
    последующая правка `app/visit_intake.py` обязана сохранить это поведение.
13. **«Отмена»**: сказать «отмена» в середине интервью (после 2–3 полей) — интервью прерывается без
    записи в журнал. Следующее «оформите визит» должно начать НОВОЕ интервью с первого вопроса (выбор
    языка) — старые частичные ответы не должны просачиваться.
14. **Guard-kb**: спросить про кабинет, реально прописанный в `config/guard-kb.yaml` (например «где
    кабинет 305?») — ответ должен точно совпасть с данными файла (этаж, отдел, примечание). Спросить про
    заведомо отсутствующий кабинет — робот должен честно сказать, что не знает, и предложить обратиться к
    охраннику, а не придумывать этаж.

## Операторский сайт (`web-src/` → собирается в `web/`)

Перенесены почти дословно: `WallPage.tsx` (ручной пульт для R1, `MotionButton.tsx`, `labels.ts`), `GuardPage.tsx`

Сознательно **не** перенесено: кнопка «Оформить визит» с панели (заставить Gemini Live проактивно заговорить

Бэкенд (`app/api_routes.py`, `app/auth.py`) не менялся — только в `app/main.py` статика заменена на SPA-fallback

15. **Навигация по профилю**: `ROBOT_PROFILE=r1` → в таб-баре виден только пункт «Видеостена»; `ROBOT_PROFILE=g1`
    → только «Охрана».
16. **Видеостена**: открыть `/wall`, нажать кнопку раздела — статус должен показать «На связи», в журнале
    команд — `accepted`. Без запущенного `wall-agent` — статус «Нет связи», команда возвращает ошибку, а не
    зависает.
17. **Охрана — панель**: пройти опрос визита голосом до конца → карточка появляется на `/guard` в «Новых»

    страницы остаётся там (значит, действительно записалось в `data/visits.jsonl`, а не только в памяти
    браузера).
18. **Токен**: задать `ACCESS_TOKEN` → операции с `/api/visits*`/`/api/wall/command` без токена падают с 401,
    модалка на странице просит его при первом обращении. Убрать `ACCESS_TOKEN` (пусто по умолчанию) — всё
    работает, модалка при желании закрывается пустым сохранением.
19. **Прямой заход/обновление страницы**: открыть `/wall` или `/guard` сразу (не через клик по табу) и нажать
    F5 — должна открыться нужная страница, а не 404 (проверка SPA-fallback в `app/main.py`).
20. **Камера не падает**: с `PRESENCE_ENABLED=true` и правильным `LD_LIBRARY_PATH`/`CYCLONEDDS_URI` —
    `VideoClient.GetImageSample()` не должен сегфолтить процесс целиком (тот же класс проверки, что раньше
    делали для `AudioClient`).
21. **Приветствие по присутствию**: встать перед роботом → в течение нескольких секунд должна прийти голосовая реплика
    без предшествующего вопроса пользователя и без `tool_call` (это обычный текстовый ход от
    `PRESENCE_MARKER`, не вызов инструмента) — на языке и в характере активного профиля.
22. **Cooldown**: уйти и вернуться раньше `PRESENCE_REARM_S` секунд — повторного приветствия быть не должно;
    вернуться позже — должно появиться снова.
23. **Камера на сайте**: открыть «Главная» — картинка с камеры должна показаться (или, если камеры нет/SDK не
    настроен, честное «Камера недоступна — нажмите, чтобы повторить», а не бесконечная серая рамка). Работает
    независимо от `PRESENCE_ENABLED`. Открыть несколько вкладок одновременно — не должно быть по отдельному
    опросу DDS на каждую (см. серверный лог `camera-hub`, если сомневаетесь).
24. **Общее приветствие предлагает выбор языка (профиль g1)**: заговорить с роботом первой репликой ВНЕ
    оформления визита (например поздороваться и сразу спросить про режим работы) — до содержательного ответа
    робот должен сначала спросить, на каком языке общаться (по-русски/по-казахски/по-английски), а не просто
    ответить.
    Профиль r1 этот вопрос задавать не должен — его ТЗ этого не требует.
25. **Микрофон робота — глобальный переключатель**: с `AUDIO_INPUT=robot` включить встроенный микрофон в одной
    вкладке (выбрать «Встроенный (робот)» → Start), затем открыть сайт во ВТОРОЙ вкладке (или обновить первую) —
    статус должен сразу показать «слушает (микрофон робота)» без повторного нажатия Start (см.
    `robot_mic_active` в сообщении `capabilities`). Нажать «Stop» в любой из вкладок — микрофон должен
    выключиться для всех, а не только для той вкладки, где нажали (проверяется по серверному логу
    `robot_mic_state.active_source -> browser` и по факту, что робот перестаёт реагировать на голос).
    С заданным `USB_MIC_ALSA_DEVICE` — то же самое для пункта «Внешний (USB)» (`usb_mic_active`), и дополнительно:
    включить «Встроенный (робот)», затем переключить на «Внешний (USB)» — робот должен слушать ТОЛЬКО через USB
    (проверить по `robot_mic_state.active_source -> usb` в логе), а не оба источника одновременно.
26. **Плановое обновление сессии Gemini**: выставить `MAX_SESSION_DURATION_S=20` (или другое маленькое
    значение) и вести разговор дольше этого времени — после ближайшего завершённого хода (`turn_complete`)
    в логе должно появиться `gemini.connection_state state=closed detail=proactive session refresh` НА
    УРОВНЕ INFO (не warning), сразу за ним — новые `connecting`/`connected` без задержки, и следующий вопрос
    должен ответить нормально (контекст разговора при этом обнуляется — это ожидаемо). Без этой настройки
    Gemini рвёт долгую сессию сам кодом 1008 — ощущается как нарастающая задержка ответа и обрыв под конец;
    цель этого пункта — подтвердить, что переключение происходит ДО того, как это случится, и не звучит как
    обрыв ответа.
27. **Одна сессия на несколько вкладок**: открыть сайт в двух вкладках (или на двух устройствах) одновременно.
    Задать вопрос голосом/текстом в первой — во ВТОРОЙ вкладке в транскрипте должна появиться та же реплика
    (это не «у каждой вкладки свой разговор» — обе смотрят в один и тот же `SessionHub`). Открыть ТРЕТЬЮ
    вкладку позже — она должна сразу увидеть уже накопленный транскрипт/tool-лог, а не пустую страницу.
    Закрыть одну из вкладок — у оставшихся разговор должен продолжаться без сбоев (в логе — никакого
    `adapter.close()`/пересоздания сессии на обычное закрытие вкладки). Нажать «Замолчи» в одной вкладке —
    робот должен замолчать даже для тех, кто смотрит с других устройств.
28. **Токен на /ws/session**: задать `ACCESS_TOKEN`, открыть сайт с корректным токеном — работает как обычно.
    Открыть `ws://<robot>:8000/ws/session` напрямую (например `websocat`/питоновским скриптом) без `?token=`
    — соединение должно закрыться сразу с кодом `4401`, не приняв ни одного сообщения. Открыть сайт с неверным
    токеном в localStorage — должно вылезти то же самое окно «Токен доступа», что и при 401 от REST.
29. **Автозапуск и автовосстановление** (`deploy/realtimevoice-{r1,g1}.service`, см. `DEPLOYMENT.md`):
    `systemctl --user restart realtimevoice-r1.service` (или `-g1`) — сайт должен снова ответить в течение
    нескольких секунд. Найти PID воркера (`systemctl --user show -p MainPID`) и `kill -9` его дочерний
    процесс — `systemctl --user status` должен показать новый PID и `active (running)` без ручного
    вмешательства, сайт должен снова ответить.
30. **Перебивание обрывает речь сразу** (`AUDIO_OUTPUT=robot`): задать вопрос, на который робот отвечает
    длинной фразой, и заговорить в середине — робот должен замолчать в течение доли секунды, а не договорить
    фразу до конца. То же самое кнопкой «Замолчи». Проигрывание вынесено в отдельную задачу
    (`SessionHub._drain_speaker`), поэтому цикл событий больше не блокируется на время речи.
31. **Опрос визита переживает пересоздание сессии (профиль g1)**: начать оформление визита, ответить на 2–3
    вопроса и подождать, пока в логе появится `gemini.connection_state state=connected` (пересоздание сессии —
    можно ускорить, выставив маленький `MAX_SESSION_DURATION_S`). Робот должен коротко извиниться за паузу,
    ПОВТОРИТЬ последний незакрытый вопрос и продолжить опрос с того же места — уже названные ФИО/организация
    не должны потеряться, повторного «начнём оформление» быть не должно. В логе — `session_hub.intake_resumed_after_reconnect`,
    а во время самого опроса плановое обновление сессии откладывается (`session_hub.refresh_deferred`).
32. **Медленный клиент не тормозит робота**: открыть сайт, затем создать проблемному клиенту сетевые условия
    (например, приостановить вкладку в браузере или уйти в зону плохого Wi-Fi) — голосовой диалог у робота и
    у остальных вкладок должен идти без задержек. При переполнении очереди такого клиента в логе появится
    `session_hub.subscriber_too_slow`, но на самого робота это влиять не должно.

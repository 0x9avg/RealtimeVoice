# RealtimeVoice

Голосовой ИИ-контур для роботов Unitree R1 (презентатор у видеостены) и G1 (помощник поста охраны): браузер
или аппаратный микрофон робота захватывает речь и текстовый ввод, FastAPI backend держит сессию Gemini Live
API (аудио-в/аудио-из, с tool calling) и отдаёт аудио-ответ обратно — в браузер или на динамик робота. Один
и тот же код обслуживает обе роли — разными профилями (`ROBOT_PROFILE=r1`/`g1`), см. раздел «Профили».

Для деплоя, запуска и настройки на роботе — `DEPLOYMENT.md`. Этот файл — архитектура и объяснение инженерных
решений: зачем сделано именно так, что откуда переиспользовано, что проверять при изменениях.

Зачем именно так и что из этого переиспользовано из соседнего репозитория — см. `../CLAUDE.md`. Протокол
общения с Gemini Live (WS-URL, формат `setup`/`realtimeInput`/`clientContent`/`toolCall`/`toolResponse`)
переиспользован из уже проверенной в бою реализации в
`../../humanoid-robot/packages/humanoid-robot-adapters-live-gemini/`, а не написан с нуля.

## Архитектура

```
Browser #1 ─┐                              FastAPI backend (app/)                Gemini Live API
Browser #2 ─┼─ /ws/session (WS) ──▶  app/session_hub.py: SessionHub  ──send_audio──▶  GeminiLiveAdapter ──▶ BidiGenerateContent
Browser #N ─┘                        (ОДНА на весь процесс,          ◀──audio/toolCall/turn───────────────
            ◀── broadcast всем ──    живёт с запуска сервера,
                подписчикам          не привязана к соединению)
                                              ToolRegistry.dispatch() ──▶ get_current_time / …
```

**Одна сессия на процесс, не на соединение.** `SessionHub` — единственный экземпляр `GeminiLiveAdapter` +
набор инструментов + (если включено) реальные микрофон/динамик робота, создаётся один раз при старте сервера
(`app/main.py`'s lifespan) и живёт независимо от того, сколько браузеров сейчас подключено — хоть ноль, хоть
несколько. `/ws/session` — это просто подписка на неё: `SessionHub.join()` регистрирует сокет, шлёт ему
текущие `capabilities` и реплеит недавнюю историю (транскрипт/tool-события, до 300 последних сообщений) —
поэтому вкладка, открытая позже остальных, видит ТУ ЖЕ страницу, а не пустой транскрипт. Любое управляющее
действие (текст, `mic_source`, `mute`) от любой вкладки действует на общую сессию; `SessionHub.leave()` при
отключении просто убирает сокет из списка подписчиков — сама сессия, микрофон и разговор с Gemini продолжают
работать для всех остальных (и для самого робота, даже если ни одна вкладка не открыта). До этого изменения
каждое WS-соединение поднимало СВОЙ `GeminiLiveAdapter`+`RobotSpeaker`+`RobotMic` — две открытые вкладки означали
два независимых разговора и попытку одновременно рулить одним и тем же физическим микрофоном/динамиком.

Ресемплинг делает сам браузер: `AudioContext` для захвата создаётся с `sampleRate: 16000`, для воспроизведения —
с `sampleRate: 24000`, поэтому на backend нет никакой обработки аудио, только пересылка байтов.

Непрерывный разговор без push-to-talk: пока микрофон включён, аудио стримится постоянно, конец хода определяет
серверный VAD самой Gemini Live. Barge-in: событие `interrupted` от Gemini backend пересылает в браузер как
`{"type":"interrupted"}`, а тот сразу останавливает и очищает очередь воспроизведения.

## Быстрый запуск для разработки

Полная процедура для реального робота — в `DEPLOYMENT.md`. Здесь — минимум для локальной работы над кодом:

1. Скопируйте `.env.r1.example` (или `.env.g1.example`) в `.env` и впишите свой `GEMINI_API_KEY` (ключ Google
   AI Studio с доступом к Gemini Live API).
2. Установите зависимости и запустите сервер:

   ```bash
   uv sync
   uv run uvicorn app.main:app --reload
   ```

3. Откройте `http://localhost:8000` в Chrome или Edge (нужны `getUserMedia` и `AudioWorklet`).

## Видеостена (`control_video_wall`)

Голосовой backend никогда не трогает MinTrans/Factories.exe напрямую — он говорит по HTTP с отдельным
процессом-агентом (`app/wall/`, `WALL_AGENT_URL` в `.env`), а тот уже знает, как управлять приложением. Это
разделение и есть то, что делает решение сетевым: backend и агент видеостены могут стоять на разных машинах.

Запуск агента — отдельным процессом, с выбором драйвера:

```bash
uv run python -m app.wall --driver sim --port 8093     # симулятор — любая ОС, для разработки
uv run python -m app.wall --driver pipe --port 8093     # реальный Factories.exe — только Windows
```

- **`sim`** — модель приложения в памяти (тот же процесс, что использовался при разработке этого прототипа).
  Ничего не требует, работает где угодно, ничего реально не переключает.
- **`pipe`** — управляет настоящим Factories.exe через его собственный именованный пайп
  (`S.Networks.Pipes.Unity.MinTrans`), реверс-инжинирнутый из `Assembly-CSharp.dll` и подтверждённый вживую
  (02.09.2026: `MENU_AERO1`/`MENU_JD2` реально переключили сцену, со скриншотами). Работает только если **сам
  процесс агента** запущен на Windows — это не WSL-хак: обычный `open(r"\\.\pipe\...")` в Python, потому что
  именованные пайпы принципиально локальны для машины. На Linux/WSL `--driver pipe` сразу и честно откажет с
  понятной ошибкой вместо того, чтобы притворяться рабочим.

Чтобы голос реально управлял стеной: разверните `app/wall` на Windows-ПК стены рядом с Factories.exe
(`uv run python -m app.wall --driver pipe`, или см. ниже — готовый `wall-agent.exe`, если на этом ПК не хочется
ставить Python), а в `.env` голосового backend'а (который может работать на любой другой машине в той же сети)
укажите `WALL_AGENT_URL=http://<адрес-пк-стены>:8093`. Код `control_video_wall` (`app/tools.py`) не меняется —
он всегда просто обращается к `WALL_AGENT_URL`, независимо от того, что за драйвер и где физически стоит агент.

### Видеостена — установка на Windows без Python (`wall-agent.exe`)

ПК видеостены обычно принадлежит контрагенту, который поставил Factories.exe, и ставить туда Python/uv вручную
неудобно каждый раз. `scripts/build_wall_agent_windows.bat` собирает `app/wall` в один файл `wall-agent.exe`
через [PyInstaller](https://pyinstaller.org/) — дальше на ПК стены нужен только этот файл, ни Python, ни uv,
ни `pip install` там не требуются вообще.

**Сборка exe — один раз, на ЛЮБОЙ Windows-машине с [uv](https://docs.astral.sh/uv/)** (не обязательно на самом
ПК стены — например, на ноутбуке разработчика):

```bat
scripts\build_wall_agent_windows.bat
```

Результат — `dist\wall-agent.exe` (один файл, ничего больше не нужно копировать для запуска). Пересобирайте
после любых изменений в `app/wall/`.

**На самом ПК стены** — скопируйте `dist\wall-agent.exe` и, для удобства, `scripts\run_wall_agent.bat` (запускает
exe с `--driver pipe --port 8093` без необходимости каждый раз набирать команду в консоли — впишите
`WALL_AGENT_TOKEN` в начале файла, если нужен `X-Wall-Token`) в одну папку рядом с Factories.exe. Дальше — просто
двойной клик по `run_wall_agent.bat` (или по самому `wall-agent.exe`, если параметры по умолчанию устраивают).
Для автозапуска при включении ПК — обычный ярлык на `run_wall_agent.bat` в `shell:startup`; отдельного механизма
автозапуска (Task Scheduler и т.п.) этот прототип не настраивает, только сам exe/bat.

Это **не** установщик самого Factories.exe или Windows-агента для звука/видеостены как системной службы —
только удобная сборка `app/wall` без ручной установки Python на машину, где он итак не нужен ни для чего
другого. Один и тот же exe работает независимо от того, какая машина в сети слушает `WALL_AGENT_URL` —
топология из абзаца выше не меняется.

Известные ограничения реального приложения (подтверждены реверс-инжинирингом `level0`, не выдуманы):
раздел `Avto5` не имеет pipe-команды вообще, `open_section` для него корректно отклоняется. Пошаговое
переключение разделов и слайдов вперёд/назад (`next_section`/`prev_section`/`next_slide`/`prev_slide`)
**не реализовано нигде** — ни в `WallNavAction` (`app/wall/commands.py`), ни в драйверах, ни в инструменте ИИ,
ни на странице «Видеостена»: в реальном приложении для этого нет ни одной pipe-команды (слайды слушают только
PgUp/PgDn напрямую), и сами разделы внутри категории не имеют содержательного порядка, чтобы «следующий»/
«предыдущий» вообще что-то значили. Остаётся только открыть конкретный раздел/категорию по имени —
`open_section`/`open_category` — и `navigate` с единственным действием `main_menu`.

## Запуск на роботе (реальный микрофон/динамик через `unitree_sdk2py`)

`app/robot_audio.py`'s `RobotSpeaker` требует нативный вендорский SDK (`unitree_sdk2py` + CycloneDDS с
поддержкой iceoryx/shared-memory). На этом роботе на диске есть **две разные сборки CycloneDDS**, и от того,
какую из них реально загрузит процесс, зависит, заработает вывод звука через колонку робота или упадёт
сегфолтом:

- `/usr/local` — вендорская сборка, идёт в паре с демоном `/usr/local/bin/iox-roudi` (нужен и ему, и всей
  остальной робото-платформе). **Несовместима** с python-пакетом `cyclonedds`, поставленным обычным
  `uv pip install cyclonedds` — падает сегфолтом внутри `iox_pub_publish_chunk` на первом же RPC-вызове
  (`AudioClient.SetVolume`/`Init`), даже если `iox-roudi` запущен и сконфигурирован правильно. Это не баг
  этого прототипа и не баг конкретной версии python-пакета — несовпадение ABI между тем, как каждая из сборок
  трактует внутренние структуры CycloneDDS при передаче данных через iceoryx.
- `~/cyclonedds_ws/install/cyclonedds` — отдельная сборка CycloneDDS из исходников (colcon/ROS2-стиль), собрана
  именно по инструкции самого `unitree_sdk2_python` (`CYCLONEDDS_HOME` перед `pip install cyclonedds`, а не
  просто `pip install cyclonedds` вслепую). **С этой сборкой всё работает.**

Поэтому перед запуском с `AUDIO_OUTPUT=robot` (или `AUDIO_INPUT=robot`, хотя вход не использует DDS вообще —
только UDP-мультикаст, ему это не нужно) обязательно экспортировать:

```bash
export LD_LIBRARY_PATH=/home/unitree/cyclonedds_ws/install/cyclonedds/lib:$LD_LIBRARY_PATH
export CYCLONEDDS_URI=/home/unitree/cyclonedds_ws/cyclonedds.xml
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

**Не полагайтесь на `.bashrc`** — там `LD_LIBRARY_PATH` указывает на `/usr/local` (нужно остальной
робо-платформе), а не на `cyclonedds_ws`, и `.bashrc` в любом случае не подхватывается неинтерактивными
SSH-командами (`ssh host 'command'`) — только явный `export` в самой команде запуска. Если после
`uv sync`/переустановки зависимостей звук на роботе снова начал падать сегфолтом — почти наверняка `cyclonedds`
пересобрался/переустановился без этого `LD_LIBRARY_PATH` и слинковался не с той библиотекой; переустановка
самого пакета не нужна, достаточно правильного `LD_LIBRARY_PATH` при запуске.

### Внешний USB-микрофон (`AUDIO_INPUT=usb`)

Помимо головного массива микрофонов (`AUDIO_INPUT=robot`, DDS/мультикаст, см. выше) и микрофона браузера,
`app/robot_audio.py`'s `UsbMic` умеет читать **любой обычный USB-микрофон, подключённый к бортовому компьютеру
робота напрямую** — ALSA видит его как обычную звуковую карту, вендорский SDK тут не нужен вообще. Проверено
вживую на этом R1 (04.09.2026): конференц-микрофон Jabra Speak2 40 MS определился как `card 2 [MS]` (`arecord
-l`/`cat /proc/asound/cards`), запись `arecord -D hw:MS,0 -f S16_LE -r 16000 -c 1` даёт настоящий (не тишина —
замеренный RMS/max на образце в 2с подтвердил реальный сигнал) моно PCM16 16кГц — тот же формат, что Gemini Live
ждёт на входе, ресемплинг не нужен.

Включается через `AUDIO_INPUT=usb` плюс ALSA-ID устройства:

```bash
AUDIO_INPUT=usb
USB_MIC_ALSA_DEVICE=hw:MS,0   # ALSA-ID карты, НЕ числовой индекс — см. .env.*.example
```

**2026-09-06, по двум прямым запросам заказчика** ("единый выбор микрофона... работает или/или... оператор сам
выбирает" и следом "микрофон... выбирается не посредством .env файла, а напрямую на сайте"): раньше
`USB_MIC_ALSA_DEVICE` включал прослушивание слова пробуждения на USB-микрофоне **независимо** от `AUDIO_INPUT` —
значит `AUDIO_INPUT=robot` вместе с заданным `USB_MIC_ALSA_DEVICE` заставляли ОБА микрофона одновременно слушать
слово пробуждения (два независимых экземпляра `WakeWordDetector`, два параллельных прогона faster-whisper, и
неочевидно, какой из них реально разбудит робота).

Теперь оба аппаратных микрофона (встроенный и USB, если `USB_MIC_ALSA_DEVICE` задан) всегда конструируются
вместе, как только `AUDIO_INPUT` — `"robot"` или `"usb"` (тот же приём, что уже применяется к `_speakers` для
`AUDIO_OUTPUT`, см. ниже) — но слушать слово пробуждения в любой момент разрешено ровно ОДНОМУ из них
(`app/session_hub.py`'s `_hw_mic_owns_wake_window`'s `_preferred_mic_input`). `AUDIO_INPUT` в `.env` задаёт только
НАЧАЛЬНЫЙ выбор при старте процесса — переключить, какой микрофон слушает, можно прямо на сайте («Главная»), без
перезапуска и без правки `.env`.

**2026-09-06, следом** ("объедини выбор... в один выбор микрофона... без разделения"): на сайте это ОДИН блок
«Микрофон», не два — кнопки «Встроенный»/«Внешний (USB)» (показываются, только когда оба реально сконфигурированы)
задают `preferred_mic_input`, а кнопка **«Разбудить»** (одна, не по кнопке на источник) — ручной оверрайд, всегда
целится в ТЕКУЩИЙ выбор из того же блока (`app/session_hub.py`'s `handle_mic_source`, вызванный с
`preferred_mic_input`), не в отдельно кликнутый источник. Раньше это были два отдельных блока с двумя разными
наборами кнопок «Разбудить (X)» — путаница, которую как раз убирает объединение. Это всё ещё **отдельно** от
глобального переключателя `app/robot_mic_state.py` (какой источник сейчас реально ПЕРЕСЫЛАЕТ звук в Gemini в
моменте) — это внутреннее состояние, не отдельная кнопка на сайте.

Реализовано через субпроцесс `arecord` (`alsa-utils`, уже стоит на роботе), а не через Python ALSA/PortAudio
биндинг — не требует новой зависимости в `pyproject.toml`. Если конкретное устройство пропадёт (отключили USB)
— `UsbMic.stream()` завершится штатно (лог `usb_mic.arecord_exited`), процесс не упадёт; чтобы отдать голос
снова, надо переключить источник обратно на «Микрофон браузера»/«Встроенный (робот)» на сайте.

**USB-динамик играл слишком быстро и высоко — устройство не держит заявленную частоту 24кГц** (2026-09-06, по
жалобе заказчика: "голос будто слишком быстрый и высокий"). Диагностика на живом Jabra Speak2 40 MS: сгенерировал
тон ровно на 10 секунд при 24000 Гц (частота, в которой Gemini реально отдаёт звук — `RECEIVE_SAMPLE_RATE_HZ`),
запустил `aplay -D hw:MS,0 -r 24000 -c 2 -t raw` и засёк время по часам — вместо 10 секунд получилось ~7.66с
(колонка играет примерно на 30% быстрее заявленного, отсюда и более высокий тон). Тот же тест на честных 32000 Гц
дал ~10.15с — точно. Устройство принимает `-r 24000` без единой ошибки (в отличие от проверки числа каналов
чуть ниже, которая хотя бы падает явно) — просто молча проигрывает не с той скоростью. Исправлено: `UsbSpeaker`
(`app/robot_audio.py`) теперь всегда пересэмплирует в `usb_speaker_sample_rate_hz` (`audioop.ratecv`, тот же
приём, что `RobotSpeaker._resample` уже использует для своего фиксированного железа) перед отправкой в `aplay` —
32000 по умолчанию, подтверждено именно для этого устройства; если у другого USB-динамика окажется свой
перекос — переопределяется через `USB_SPEAKER_SAMPLE_RATE` в `.env`, тем же способом измерения (сгенерировать
тон известной длины, засечь по часам факт против заявленного на нескольких частотах, взять точную).

**Известное ограничение аппаратного микрофона: голосом не прервать робота, пока он говорит.** На этом
железе нет эхоподавления (AEC) — без него робот слышал бы собственный голос через любой аппаратный микрофон
(встроенный или USB) и реагировал на самого себя. Поэтому `HalfDuplexGate` (`app/robot_audio.py`) полностью
глушит аппаратный микрофон, включая распознавание ключевого слова, на всё время, пока робот говорит, плюс
`ROBOT_POST_SPEECH_GUARD_MS` (300мс по умолчанию) после — это касается ТОЛЬКО аппаратного входа. Практическое
следствие для персонала: пока робот отвечает, посетитель не может перебить его голосом через
`AUDIO_INPUT=robot`/`usb` (нужно дождаться конца фразы) — единственный способ прервать ответ мгновенно голосом
уже во время воспроизведения — кнопка **«Замолчи»** на сайте (она не зависит от состояния аппаратного
микрофона) либо текстовый ввод. Это ограничение железа, а не баг конкретной сборки; стоит заранее
предупредить об этом заказчика/охрану, чтобы «робот не реагирует, пока говорит» не выглядело поломкой.

### Камера и реакция на посетителя (`app/robot_camera.py`, `app/camera_hub.py`, `app/presence.py`)

Камера G1 физически висит на другом бортовом компьютере, не на Jetson — здесь нет `/dev/video*` вообще
(проверено: `lsusb`, `lsmod`, нет `uvcvideo`). Доступ — через `unitree_sdk2py.go2.video.video_client.VideoClient`
поверх DDS (тот же `go2`-неймспейс, что и с `g1_audio_client` — Unitree не сделал отдельного видео-модуля для
G1), тот же класс DDS RPC-клиента, что и `AudioClient`, и требует **тот же фикс**, что и звук:

```bash
export LD_LIBRARY_PATH=/home/unitree/cyclonedds_ws/install/cyclonedds/lib:$LD_LIBRARY_PATH
export CYCLONEDDS_URI=/home/unitree/cyclonedds_ws/cyclonedds.xml
```

**Проверено вживую на роботе** (03.09.2026): `VideoClient.GetImageSample()` с этим окружением не падает и
отдаёт реальный JPEG 1280×720. **Важно**: это широкоугольный (рыбий глаз) вид **вниз**, на пол и ближайшие
предметы — похоже, это утилитарная/навигационная камера (`go2`-неймспейс — вероятно, камера квадропеда для
объезда препятствий), а не «глаза» на уровне человека. Годится, чтобы увидеть, что происходит рядом с
роботом, но для «замечает подходящего издалека посетителя» может не подойти — это открытый вопрос к
железу/установке, не к коду.

`app/camera_hub.py`'s `CameraHub` — единственный опрос DDS на процесс (по образцу `FrameHub` из
`../../humanoid-robot`'s `camera_mjpeg.py`): и просмотр на сайте, и детекция присутствия читают из одного и
того же опроса, а не заводят по своему клиенту каждый — иначе два независимых опроса одного DDS-сервиса.

**Просмотр камеры на сайте**: `GET /api/camera/snapshot` (один кадр) и `GET /api/camera/stream` (MJPEG,
`multipart/x-mixed-replace` — то, что рендерит `<img>` на странице «Главная», `components/CameraView.tsx`)
работают **независимо от `PRESENCE_ENABLED`** — хаб стартует лениво при первом запросе.

**Автоприветствие**: как только `MotionDetector` (покадровое вычитание в градациях серого, без ML —
перенесено из `../../humanoid-robot/apps/presence`) фиксирует устойчивое движение, в активную голосовую сессию
уходит `adapter.send_text(PRESENCE_MARKER)` — модель сама, по системной инструкции (`app/scenarios.py`),
естественно здоровается в характере своего профиля. Выключено по умолчанию (`PRESENCE_ENABLED=false`) — сам
доступ к камере проверен, а вот полный путь «движение → голосовое приветствие» вживую ещё не прогонялся, плюс
открыт вопрос по углу обзора выше.

```bash
export PRESENCE_ENABLED=true
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Настройки: `PRESENCE_CAMERA_IFACE` (по умолчанию `eth10`), `PRESENCE_THRESHOLD` (`0.02`), `PRESENCE_REARM_S`
(`60.0`), `PRESENCE_FPS` (`2.0`, темп опроса самим детектором) и `PRESENCE_CAMERA_FPS` (`8.0`, темп опроса
хабом — от него зависит плавность картинки на сайте). `MotionDetector`/`PresenceRunner`/оба варианта скорера
проверены юнит-тестом (`tests/test_presence.py`) на синтетических кадрах (без камеры) — включая реальный
спавн/убийство/рестарт дочернего процесса для `SubprocessMotionDetector`.

**Изоляция детекции присутствия в отдельный процесс** (пункт из списка UX-правок 2026-09-06: «это должен быть
отдельный процесс от генерации речи и слушания, чтобы не возникало задержек... и он не тормозил основной
контур»). `PRESENCE_ISOLATION=process` (по умолчанию) запускает покадровое вычитание не потоком внутри
основного процесса, а отдельным ОС-процессом `python -m app.presence_worker` (`app/presence_worker.py`) —
`app/presence.py`'s `SubprocessMotionDetector` общается с ним через stdin/stdout по протоколу с префиксом
длины (JPEG-кадр → float32-оценка). `CameraHub` при этом остаётся единственным опросом DDS — воркер сам камеру
не трогает, кадры ему передаёт родительский процесс. Если воркер падает или зависает, `score()` тихо
перезапускает его и возвращает `0.0` за тот один кадр — вызывающий код (`PresenceRunner`) никогда не видит
исключения из-за сбоя воркера. `PRESENCE_ISOLATION=thread` возвращает старое поведение — тот же скорер, но
`asyncio.to_thread` внутри этого же процесса (`LocalMotionDetector`), без отдельного процесса; полезно для
локальной разработки/тестов, где спавнить второй `python -m` процесс на каждый тест не нужно.

`app/session_hub.py` (одна сессия на процесс, живёт с момента старта сервера — см. «Архитектура» выше) слушает/
говорит автономно, без открытого браузера — сайт (`app.main`) остаётся единственной точкой входа, но не
обязателен, чтобы робот продолжал работать: голосовой контур не зависит от того, открыта ли сейчас страница у
кого-то в браузере. Отдельный headless-раннер (`app.robot_main`) существовал до 2026-09-04 именно на случай
«без сайта вообще» — убран как избыточный (пункт 2 списка правок): браузерная панель — теперь единственная и
основная панель управления, а не одна из двух равнозначных.

## Продакшн-развёртывание (автозапуск, Wi-Fi, защита API)

Пошаговые процедуры — в `DEPLOYMENT.md`. Здесь — инженерные решения, стоящие за ними.

**Автозапуск** — `deploy/realtimevoice-{r1,g1}.service`, юниты **пользовательского** systemd
(`~/.config/systemd/user/`, не `/etc/systemd/system/`). Намеренный выбор: не требует root/sudo вообще, в
отличие от системного systemd — актуально, если у пользователя, от которого работает сервис, нет
passwordless sudo. `Restart=on-failure` — если процесс упадёт (в т.ч. зависнет в блокирующем DDS-вызове и
получит `kill -9`) — systemd поднимет его заново сам, без ручного вмешательства через SSH.

Дополнительная сеть надёжности внутри самого процесса: `app/session_hub.py`'s фоновые задачи
(`_pump_gemini`/`_robot_mic_task`/`_usb_mic_task`/`_drain_speaker`) обёрнуты в супервизор — если какая-то из
них всё же упадёт необработанным исключением, процесс сам завершится (`os._exit`), и systemd поднимет чистый
заново — вместо «сайт вроде отвечает, а робот навсегда замолчал» (процесс жив, но один из фоновых циклов молча
умер — снаружи неотличимо от нормальной работы, пока кто-то не заговорит с роботом и не получит тишину).
`_presence_task` — единственное исключение: он **не** обёрнут в супервизор, а сам ловит всё и ретраит с
задержкой (см. его докстринг) — это дополнительная фича поверх голосового контура (2026-09-06: «это скорее
дополнение»), не путь работы с железом вроде микрофона/динамика, без которого робот реально бесполезен, так
что баг в детекции присутствия не должен ронять весь процесс `os._exit`'ом.

**Wi-Fi**: NetworkManager с `autoconnect=yes`, `autoconnect-retries=-1` (бесконечные повторные попытки) — уже
устойчиво к обрывам связи само по себе. Отдельно стоит отключить энергосбережение Wi-Fi-адаптера
(`wifi.powersave`) — штатное поведение Ubuntu держит его включённым, что периодически просаживает связь именно
под непрерывной нагрузкой вроде голосового стриминга.

**Проверьте это на КАЖДОМ роботе отдельно, не только один раз на одном из них** (2026-09-06 находка, по
жалобе на нестабильность канала: «голос иногда запинается и очень долго отвечает») — на R1 `wifi.powersave`
был выключен, а на G1 нет: `/etc/NetworkManager/conf.d/local-wifi-powersave-off.conf` там просто не существовал,
и `iwconfig` показывал `Power Management:on`. Это ручной, разовый шаг на каждой машине (не часть деплоя кода),
и его легко забыть сделать на втором роботе после того, как настроили первый. Команда (нужен sudo, интерактивно
— агент/скрипт CI это не может выполнить сам за вас):

```bash
echo -e "[connection]\nwifi.powersave = 2" | sudo tee /etc/NetworkManager/conf.d/local-wifi-powersave-off.conf
sudo systemctl restart NetworkManager   # SSH-сессия может на секунду оборваться и переподключиться сама
```

Проверить результат: `iwconfig 2>&1 | grep "Power Management"` — должно быть `off`.

**Стабильность канала с Gemini — три независимых фикса от 2026-09-06, по той же жалобе:**

1. **`MAX_SESSION_DURATION_S` снижен с 360 до 90 секунд.** Живые логи в момент диагностики показали, что G1
   получал от Gemini принудительное закрытие сессии (`1008 policy violation`) регулярно каждые ~150 секунд —
   **три раза подряд, ни разу не дожив до собственного планового обновления на 360-й секунде** — тогда как R1
   в то же самое окно ни разу не поймал вынужденное закрытие и обновлялся сам, по расписанию, чисто. Точная
   причина, почему у G1 что бы Gemini ни считал лимитом накапливается быстрее (больше/крупнее вызовов
   инструментов на `search_guard_kb`/`visit_intake` — основной подозреваемый), не подтверждена, но чинить это
   не обязательно знанием причины: снизили порог планового обновления настолько, чтобы оно ГАРАНТИРОВАННО
   срабатывало раньше любого вынужденного закрытия, на обоих профилях, а не подбирали по одному значению на
   каждый — вынужденное закрытие ощущается посетителем как обрыв ответа на полуслове или зависание, плановое
   же полностью не слышно (случается только между репликами). Если на каком-то объекте `1008` всё равно
   проскакивает — снижайте `MAX_SESSION_DURATION_S` ещё, через `.env`/веб-мастер, без правки кода.
2. **`GeminiLiveAdapter._pump`'s гонка между приёмом и отправкой** (`app/gemini_live.py`) — раньше отправка
   исходящих сообщений (`_drain_send_queue`) и приём входящих (`async for raw in ws`) были независимы: если
   `ws.send()` падал по причине, которая НЕ ломала сразу и приёмную сторону (ничего не гарантирует, что оба
   направления одного TCP-соединения падают одновременно), задача отправки тихо умирала, а цикл приёма
   продолжал как ни в чём не бывало — снаружи это выглядело как «подключено и работает», аудио с микрофона
   копилось в очереди бесконечно, а Gemini ничего нового не слышал вообще, до тех пор пока что-то ДРУГОЕ не
   заметило проблему отдельно. Теперь `_pump` гонит обе стороны через `asyncio.wait` — сбой отправки
   немедленно обрывает цикл и переподключается, точно как уже делает сбой приёма.
3. **Context window compression** (`app/gemini_live.py`'s `_context_window_compression_config`,
   `CONTEXT_WINDOW_COMPRESSION_ENABLED` в `.env`, по умолчанию включено) — собственный механизм Gemini Live для
   той же проблемы, но со стороны самой модели: как только контекст сессии превышает
   `CONTEXT_WINDOW_COMPRESSION_TRIGGER_TOKENS`, Gemini сжимает/суммирует старые реплики сама, вместо того чтобы
   рано или поздно принудительно закрыть сессию. **Дополняет, а не заменяет** плановое обновление сессии
   (пункт 1) — то намеренно стирает ВСЮ память разговора при каждом обновлении (resumption-токен не
   используется), а это позволяет по-настоящему длинному разговору реально сохранять контекст между репликами.
   Включение этого — не повод снова поднимать `MAX_SESSION_DURATION_S` без новых данных из логов. Поле
   `contextWindowCompression` — **сосед `generationConfig` на уровне `setup`, а не вложено внутрь него**
   (сверено с официальным reference `BidiGenerateContentSetup` — лёгкая ошибка сделать наоборот); `triggerTokens`/
   `targetTokens` — обычные целые числа в JSON, не строки. Пусто (по умолчанию) — Gemini сама выбирает порог,
   как и в примерах из официального SDK; задавайте числа только если в логе видно, что сжатие срабатывает
   слишком поздно или слишком часто для реальной нагрузки.

**API открыт, без токена** (пункт 4 из списка правок 2026-09-04) — раньше `/ws/session` и `/api/*` требовали
`ACCESS_TOKEN` (`app/auth.py`, теперь удалён), это осознанно убрано целиком: ни `Authorization`, ни `?token=`
нигде не проверяются. Значит любое устройство в той же сети может подключиться к `/ws/session` напрямую и
управлять активным разговором (заглушить робота, выдать себя за текст-ввод, дёрнуть видеостену), а также читать
`/api/visits*` и слать `/api/wall/command` — сознательный компромисс в пользу простоты установки, подходит для
изолированной/доверенной сети. Если деплой окажется в сети с посторонними устройствами, потребуется вернуть
какой-то auth-слой (например, обратный прокси с basic-auth перед этим сервисом) — в самом приложении его больше
нет.

**Мастер настройки для нетехнического заказчика** (`app/installer/`, `installer/bootstrap.sh`,
`deploy/realtimevoice-setup.service`) — см. DEPLOYMENT.md §0 для пользовательского описания шагов; здесь —
почему он устроен именно так:

- **Отдельный процесс от `app.main:app`**, свой uvicorn на порту 8090, свой systemd-юнит. Он должен
  оставаться доступен, даже когда основной голосовой сервис не запущен вовсе или зациклился в падениях —
  ровно та ситуация, в которой заказчик его и открывает — и он же перезапускает/останавливает основной
  сервис через `systemctl --user`, так что имеет смысл держать эту власть в процессе с меньшим блэст-радиусом,
  чем тот, что ведёт живую сессию Gemini в браузере.
- **Не импортирует `app.config.Settings`** — тот синглтон строится один раз при импорте из уже
  существующего `.env`, а мастер как раз существует для случая, когда `.env` ещё нет или заполнен наполовину.
  Все чтения/записи идут через `app/installer/env_file.py`, который построчно обновляет только тронутые
  ключи и **не удаляет комментарии** — наивный "распарсить в dict и сериализовать обратно" стёр бы всю
  документацию из `.env.r1.example`/`.env.g1.example`.
- **Переписывает `WorkingDirectory=` при установке юнита** (`app/installer/systemd.py`'s `install_unit`) —
  шаблоны `deploy/realtimevoice-{r1,g1}.service` жёстко прописывают `%h/realtimevoice-r1`/`-g1` по
  документированной в DEPLOYMENT.md конвенции, но мастер не может полагаться на то, что нетехнический
  заказчик склонировал репозиторий именно туда; юнит копируется в `~/.config/systemd/user/` с этой одной
  строкой, переписанной на реальный путь.
- **Две страницы, один набор редакторов** (`app/installer/static/index.html`). Пока робот не настроен,
  страница работает как линейный мастер: один вопрос на экран, нумерованные шаги, финальная кнопка
  «Запустить робота». Как только настройка завершена (сервер отдаёт `setup_complete`: выбран профиль, задан
  ключ, установлен юнит), тот же адрес открывается как **меню настроек** — боковой список разделов, любой
  пункт правится отдельно. Это следствие того, что мастер проходят один раз, а меняют настройки потом
  постоянно: заставлять оператора листать шесть шагов ради одного слова пробуждения — то же самое, что
  вернуть его к ручному редактированию `.env`, только медленнее. Обе страницы используют ОДНИ И ТЕ ЖЕ
  редакторы (объект `EDITORS`: `body`/`bind`/`save` на каждую тему) — второй реализации «как править слова
  пробуждения» нет намеренно, именно через неё две страницы и разошлись бы.
- **`setup_complete` не требует, чтобы служба была запущена прямо сейчас.** Остановленная или упавшая служба
  — это по-прежнему настроенный робот, и возвращать его владельца в «Добро пожаловать 👋 / какой это робот?»
  значило бы спрятать журнал и кнопку перезапуска ровно тогда, когда они нужны.
- **Смена профиля выключает службу предыдущей роли** (`systemd.disable_now` в `POST /api/profile`) — в
  мастере это одноразовый шаг, а в меню настроек обычный пункт; оба юнита слушают один порт 8000, так что
  оставленная включённой старая служба держала бы порт, который новая пытается занять.
- **Проверка ключа Gemini** — лёгкий REST-запрос (`models.list`) к `generativelanguage.googleapis.com`, а не
  открытие настоящей `BidiGenerateContent`-сессии: секунда вместо полноценного подключения, и не тратит
  голосовую сессию впустую только ради проверки опечатки в ключе.
- **Разделение с операторской страницей (:8000) по принципу «что переживает перезапуск».** Живое
  переключение «встроенный микрофон ↔ USB» и «внутренний динамик ↔ USB» принадлежит странице робота:
  оно мгновенное и не требует ни перезапуска, ни правки `.env` руками. Мастер отвечает за то, чего та
  страница структурно не может: `AUDIO_INPUT`/`AUDIO_OUTPUT` читаются ровно один раз, в
  `SessionHub.__init__`, поэтому «есть ли у этого робота аппаратный звук вообще» — решение уровня
  перезапуска; и за имена ALSA-устройств, для которых нужны перечисление карт и тесты записи/сигнала
  (`app/installer/audio.py`) — на :8000 такой машинерии нет. 2026-09-07, по вопросу заказчика «зачем
  меню звук в панели, если управление вводом/выводом должно быть полностью в :8000»: раздел
  переименован в «Аудиоустройства» и сведён к одному переключателю аппаратного звука плюс выбору/
  проверке USB-устройств, с явной отсылкой на страницу робота — раньше он показывал тройной выбор
  «браузер/робот/USB», который читался как тот же самый живой переключатель.
- **Живой выбор источника записывается обратно в `.env`** (`SessionHub._remember_audio_choice`,
  2026-09-07). Без этого две страницы расходились ровно на перезапуске: оператор переводил микрофон на
  USB-гарнитуру перед демонстрацией, служба перезапускалась — и робот молча возвращался к встроенному
  микрофону, потому что `AUDIO_INPUT` читается один раз при старте. Запись не может включить или
  выключить аппаратный звук за спиной оператора: оба вызывающих метода отказывают в источнике, которого
  нет, а аппаратные источники существуют только если в файле уже стояло `robot`/`usb`. Ошибка записи
  (например, checkout только для чтения) логируется и не ломает уже состоявшееся переключение.
- **Аудио-тест — не просто ОК/ошибка**: запись с микрофона отдаётся браузеру как `audio/wav`, чтобы заказчик
  услышал именно свою тестовую запись — рабочий, но слишком тихий микрофон программно неотличим от
  реально сломанного, а на слух это очевидно сразу.
- **Не автоматизирует сборку `unitree_sdk2py`/CycloneDDS** — это подготовка конкретного железа, заранее
  выполненная интегратором (см. раздел 1 требований в DEPLOYMENT.md), не то, что можно один раз
  автоматизировать для любой машины; мастер настраивает только слой RealtimeVoice поверх уже готового робота.
- **Не редактирует `config/guard-kb.yaml` из браузера** — сознательно вне рамок: справочник поста охраны
  должен редактировать тот, кто отвечает за его достоверность (см. раздел "Профили" ниже про "не должен
  придумывать ответ"), не случайная форма в мастере настройки. Мастер только показывает, загружен ли файл
  и сколько в нём записей.
- **«Расширенные настройки» — схема, не отдельные ручные формы** (`app/installer/settings_schema.py`,
  2026-09-06 ask: "настройку всех конфигов возможных роботов ... всё, что сейчас нужно менять вручную") —
  каждое поле (ключ `.env`, подпись, подсказка, тип, группа, к какому профилю относится) описано ОДИН раз в
  этом файле как данные, а не как HTML-разметка для каждого поля вручную; `GET /api/advanced-settings`
  отдаёт схему вместе с текущими значениями (из `.env`, либо значение по умолчанию), фронтенд рисует форму
  генерически по типу поля (text/number/toggle/select). Так добавление нового настраиваемого параметра — это
  одна запись в списке `GROUPS`, а не новый эндпоинт и кусок HTML. Схема **сознательно не включает** поля
  `Settings`, у которых на самом деле нет переменной окружения (`ws_host`, `language_code`,
  `wall_agent_timeout_s` и т.п., см. докстринг файла) — показывать редактируемое поле, которое молча ничего
  не меняет, хуже, чем не показывать его вовсе.

- **Модель Gemini Live** — по умолчанию `models/gemini-3.1-flash-live-preview`. Список доступных Live-моделей
  завязан на конкретный API-ключ/аккаунт; если подключение сразу падает с ошибкой — задайте `GEMINI_LIVE_MODEL`
  в `.env` на модель, реально доступную вашему ключу.
- **Аудио-путь** — по умолчанию звук идёт через браузер (`AUDIO_OUTPUT`/`AUDIO_INPUT=browser`): backend не
  трогает аудио-устройства напрямую, ресемплинг делает сам `AudioContext` в браузере. Для реального робота
  есть отдельный путь через аппаратный микрофон/динамик (`=robot`, поверх `unitree_sdk2py`/DDS) — см. раздел
  «Запуск на роботе».
- **Наблюдаемость** — сегодня это структурированные логи через `journalctl`/stdout (см. `DEPLOYMENT.md`,
  раздел «Управление сервисом»); отдельного JSONL event log или агрегированных p50/p95-метрик задержки нет.
  Для текущего объёма поставки (два независимых деплоя, один оператор на каждый) логов достаточно для
  диагностики; централизованный мониторинг — кандидат на следующий этап, если появится несколько объектов
  под одним наблюдением.
- **Проверка корректности** — сам голосовой контур (STT/TTS/tool-calling против реального Gemini Live API)
  проверяется только вживую — это в принципе не автоматизировать без реального API-ключа и живой модели, и
  ручной чек-лист ниже как раз для этого. Детерминированная логика без внешнего API — `app/visit_intake.py`
  (визит-интервью на двух языках, включая обязательный сброс на «нет»), `app/presence.py`'s `MotionDetector`,
  `app/session_hub.py`'s подписка/broadcast/история, устойчивость к сбоям фоновых задач — покрыта тестами
  в `tests/`, запускаются `uv run pytest`.

## Ручной чек-лист

1. Нажать **Start mic**, разрешить доступ к микрофону, сказать что-нибудь — статус должен перейти
   `listening → speaking`, должен идти звук ответа, в транскрипте — реплики.
2. Ввести вопрос текстом и нажать **Send** — должен прийти голосовой ответ без использования микрофона.
3. Спросить "который час?" / "what time is it?" — в логе tool calls должен появиться вызов `get_current_time`,
   а озвученный ответ — содержать корректное текущее время.
4. Заговорить во время проигрывания ответа (barge-in) — воспроизведение должно оборваться быстро, а не
   доиграть до конца.
5. Нажать **Замолчи** во время ответа — воспроизведение должно остановиться мгновенно.
5в. **Ровность речи.** Задать роботу вопрос, требующий длинного ответа (10+ секунд), и послушать: между
    словами не должно быть провалов. Затем `journalctl --user -u realtimevoice-r1.service | grep
    turn_pacing` — `worst_buffer_ms` должен быть близок к `lead_ms` (200). Строка уровня WARNING с
    `worst_buffer_ms` около нуля означает, что динамику было нечего играть; см. DEPLOYMENT.md §12.
5a. Мастер настройки (`bash installer/bootstrap.sh`, затем `http://<робот>:8090`) — пройти весь визард на
    чистой машине (нет `.env`) до конца: выбор профиля создаёт `.env` из нужного шаблона; тест ключа Gemini
    в отдельной вкладке через нерабочий ключ должен явно сказать, что ключ не подходит, не просто "ошибка";
    для USB-звука список устройств должен показывать человекочитаемые имена, а не `hw:X,Y`, и иметь
    пункт «— не используется —», которым устройство снимается; «Запустить
    робота» должен реально поднять systemd-юнит и через минуту показать, что порт отвечает. Затем
    перезагрузить страницу — должно открыться **меню настроек** (боковой список разделов), а не мастер с
    нуля; «Перезапустить» и «Журнал» в нём должны работать. Остановить службу («Остановить») и снова
    перезагрузить страницу — по-прежнему меню настроек, а не мастер.
5b. Меню настроек — раздел «Расширенные»: поменять одно текстовое поле (например `TOOL_TIMEOUT_S`) и один
    переключатель (например «Пробуждение по слову включено»), нажать «Сохранить всё» — оба значения должны
    попасть в `.env` (проверить файл или перезайти на страницу — поле должно показывать новое значение).
    Начать правку в разделе «Пробуждение» и, не нажимая «Сохранить», кликнуть другой раздел в боковом меню —
    правка должна сохраниться сама (в `.env`), а не потеряться. После любого сохранения при работающей службе
    вверху должна появиться полоса «Перезапустить сейчас», и она должна исчезать после перезапуска.
    Переключить микрофон на странице робота (:8000) со встроенного на USB, затем перезапустить службу —
    после перезапуска должен остаться USB (раньше молча возвращался встроенный: `AUDIO_INPUT` читается
    один раз при старте). Проверить и обратное направление, и то же самое для вывода звука.
    Переключить профиль в разделе «Робот» — служба предыдущей роли должна остановиться
    (`systemctl --user is-active realtimevoice-r1.service` → `inactive`), а в разделе «Расширенные» поля
    другого профиля (токен видеостены на G1, путь к справочнику на R1) не должны отображаться.
6. **2026-09-06 audit regressions.** Перезапустить сервис (`systemctl --user restart
   realtimevoice-r1.service`) с открытой вкладкой браузера — вкладка должна сама переподключиться в течение
   секунд (баннер «Нет связи с роботом — переподключаюсь…»), без перезагрузки страницы, и если браузерный
   микрофон был включён — снова заработать без повторного нажатия **Start mic**. На G1: ответить на вопрос
   о пропуске/удостоверении фразой, содержащей «не надо» (например «нет, не надо») — интервью НЕ должно
   отмениться. Спросить у робота что-то, что несколько раз подряд переключает видеостену (R1) — латентность
   каждой команды не должна расти от предыдущих (нет пересоздания HTTP-клиента на каждый вызов).
7. **Единый выбор микрофона для wake-up, переключаемый на сайте** (2026-09-06, по трём запросам заказчика:
   "разделения и параллельного слушания не должно быть, работает или/или, оператор сам выбирает" + "выбирается
   не посредством .env файла, а напрямую на сайте" + "объедини выбор... в один выбор микрофона... без
   разделения"): задать одновременно `AUDIO_INPUT=robot` и `USB_MIC_ALSA_DEVICE=hw:MS,0` — при старте обе модели
   `wake_word.model_loaded` загрузятся (это нормально, обе всегда готовы), но в логе `faster_whisper: Processing
   audio` должны появляться строки только от ОДНОГО источника — того, что выбран стартовым (`AUDIO_INPUT`). На
   сайте («Главная») должен быть ОДИН блок «Микрофон» с кнопками «Встроенный» / «Внешний (USB)» — нажать на
   невыбранный вариант, без перезапуска службы и без правки `.env`, и с этого момента строки `Processing audio`
   должны идти уже от ДРУГОГО источника, а от прежнего — прекратиться. В том же блоке одна кнопка «Разбудить»
   (не по кнопке на источник) — должна будить именно ТЕКУЩИЙ выбранный вариант, а не всегда один и тот же.
8. **Стабильность канала с Gemini** (2026-09-06, по жалобе «голос иногда запинается и очень долго отвечает»):
   на каждом роботе `iwconfig | grep "Power Management"` должен показывать `off` — если `on`, применить фикс из
   раздела «Продакшн-развёртывание» (нужен sudo, руками, один раз на каждой машине). Оставить сервис работать
   10+ минут без разговора — в логе не должно быть `1008 (policy violation)` (только `proactive session
   refresh` каждые ~90с). Затеять разговор подлиннее и специально не отвечать 20-30 секунд между репликами —
   мик не должен засыпать раньше `WAKE_ACTIVE_WINDOW_S` (45с по умолчанию). Провести один длинный
   многоходовой разговор (несколько вопросов подряд без пауз) — сжатие контекста должно позволить роботу
   помнить более ранние реплики этого же разговора дольше, чем позволяло бы одно только 90-секундное плановое
   обновление сессии (которое само по себе память не сохраняет).

## Профили (R1/G1), guardrail'ы и G1-инструменты

Один и тот же код обслуживает обе роли через `ROBOT_PROFILE` (`r1` по умолчанию, или `g1`) — см.
`app/config.py`, `app/scenarios.py` (тематический и языковой system_instruction), `app/tool_registry.py`
(какие инструменты регистрируются на каком профиле). `Settings` — синглтон, читается один раз при импорте,
поэтому смена профиля — это переменная окружения + перезапуск процесса, без горячего переключения.

6. **Переключение профиля**: `ROBOT_PROFILE=r1` (по умолчанию) → запустить сервер → в логах строка вида
   `session.start profile=r1 tools=[...]` с `control_video_wall`/`search_knowledge`, без `visit_intake`/
   `search_guard_kb`. Поставить `ROBOT_PROFILE=g1` → перезапустить → обратная картина. Панель tool-call
   лога в браузере (фронтенд не менялся) должна показывать только инструменты активного профиля при их
   вызове.
7. **Тематический отказ (оба профиля)**: вопрос вне разрешённой темы (например «какая погода в Алматы?»
   на r1, что-то не про визит и не про консультации на g1) → вежливый отказ с переадресацией к
   сотруднику/охраннику, без выдумывания ответа.
8. **Языковой отказ**: вопрос на языке, отличном от русского/казахского/английского (например по-французски
   или по-немецки) → робот вежливо отказывается отвечать на этом языке, объясняет по-русски, что
   поддерживает русский, казахский и английский, и НЕ замолкает и не зависает. Отдельно проверить, что
   вопрос по-английски (например "What time is it?") — теперь разрешённый язык — отрабатывает нормально и
   НЕ попадает под этот отказ, как и вопрос по-казахски.
9. **Полный happy path визита (профиль g1)** (переписано 2026-09-05 — явного вопроса о языке больше нет,
   см. пункт 4 списка правок): сказать «оформите визит» → сразу отвечать по порядку на все 6 вопросов на
   русском (ФИО → организация → цель → к кому → пропуск да/нет → удостоверение да/нет) → на зачитанную
   карточку ответить «да». Проверить: (а) озвучка на каждом шаге близка к тому, что вернул инструмент
   `visit_intake` (по логу tool-call в браузере и по отсутствию `relay_divergence`-warning в логах сервера),
   (б) в `data/visits.jsonl` появилась новая строка с корректными полями, включая `"language": "ru"`.
10. **Тот же сценарий на казахском**: сказать «оформите визит» и сразу отвечать на казахском (например
    ФИО — «Ахметұлы Асхат», содержит специфичную казахскую букву) — язык должен определиться автоматически
    по первому же ответу, все следующие вопросы и финальное зачитывание карточки — по-казахски. Завершить
    визит («иә» на подтверждении) — в `data/visits.jsonl` должна появиться запись с `"language": "kk"`.
11. **Тот же сценарий на английском**: сказать «оформите визит» и сразу отвечать на английском (например
    ФИО — "John Smith", латиница без кириллицы) — язык определяется автоматически с первого ответа, все
    следующие вопросы и финальное зачитывание карточки — по-английски. Завершить визит («yes» на
    подтверждении) — в `data/visits.jsonl` должна появиться запись с `"language": "en"`.
12. **«Нет»/«жоқ»/«no» на подтверждении открывает меню исправления одного поля, а не перезапускает всё**
    (переписано 2026-09-05, пункт 9 списка правок — сознательное отступление от прежнего буквального
    требования ТЗ, по прямому запросу заказчика). Пройти все 6 вопросов, на «Всё верно?» ответить «нет» —
    робот должен спросить, что именно поправить (ФИО/организация/цель/к кому/пропуск/удостоверение).
    Назвать одно поле (например «организация») — робот переспрашивает только его, затем зачитывает
    ОБНОВЛЁННУЮ карточку, где остальные пять полей не изменились. Подтвердить «да» — только тогда должна
    появиться запись в `data/visits.jsonl`, с исправленным полем и нетронутыми остальными. Отдельно
    проверить путь эскапа: на меню исправления сказать «заново» — интервью должно начаться с первого
    вопроса (ФИО), как в старом поведении.
13. **«Отмена»**: сказать «отмена» в середине интервью (после 2–3 полей) — интервью прерывается без
    записи в журнал. Следующее «оформите визит» должно начать НОВОЕ интервью с первого вопроса (ФИО) —
    старые частичные ответы не должны просачиваться.
14. **Guard-kb**: спросить про кабинет, реально прописанный в `config/guard-kb.yaml` (например «где
    кабинет 305?») — ответ должен точно совпасть с данными файла (этаж, отдел, примечание). Спросить про
    заведомо отсутствующий кабинет — робот должен честно сказать, что не знает, и предложить обратиться к
    охраннику, а не придумывать этаж.
14a. **Guard-kb — изменения подхватываются без перезапуска** (UX-аудит 2026-09-06: раньше файл читался
    ровно один раз при старте процесса, в отличие от `knowledge_guard/*.md`, который уже тогда обновлялся на
    лету — правка `config/guard-kb.yaml` молча не давала эффекта до перезапуска сервиса). Не останавливая
    процесс — отредактировать этаж существующего кабинета в `config/guard-kb.yaml`, сохранить, задать тот же
    вопрос повторно — ответ должен отражать новое значение (в логе — `guard_kb.reloading`).

## Операторский сайт (`web-src/` → собирается в `web/`)

Реальный React-код, портированный из `../../humanoid-robot/web/dashboard` (React 18 + TypeScript + Vite +
Tailwind) — не переписан с нуля. Исходники — в `web-src/`, собираются в статический бандл в `web/` (его и отдаёт
FastAPI). **На роботе нет Node/npm** — собирать нужно здесь и деплоить только `web/`:

```bash
cd web-src && npm install && npm run build   # → пишет прямо в ../web, старое содержимое web/ стирается
```

**Разделы, которых на этом роботе нет, недоступны, а не просто спрятаны** (2026-09-07). Таб-бар и раньше
показывал только «свой» пункт, но маршрут оставался живым: `/wall`, набранный вручную на G1 (или открытый по
старой закладке, или по ссылке из инструкции к R1), разворачивал полноценный пульт видеостены на роботе, у
которого видеостены нет — и каждая его кнопка потом упиралась в ненастроенного агента. Теперь закрыты обе
двери: страница чужого профиля перебрасывает на «Главную» (`ProfileRoute` в `web-src/src/App.tsx`), а
обслуживающий её API отвечает 404 (`only_on` в `app/api_routes.py`) — `/api/wall/*` только на R1,
`/api/visits*` только на G1. Именно 404, а не 403: со стороны оператора этого раздела на его роботе
действительно не существует. Сам `index.html` по чужому пути по-прежнему отдаётся — так переброс делается на
стороне клиента, и старая закладка приводит на рабочую страницу, а не в тупик.

Для разработки с горячей перезагрузкой: `cd web-src && npm run dev` (порт 5173, проксирует `/api` и `/ws` на

    ОДНОЙ фразой без паузы, например «Робот, оформите визит пожалуйста» — сама фраза-триггер, произнесённая в
    том же дыхании, что и остальной запрос, не должна потеряться. Технически: `WakeWordDetector.feed()`
    (`app/wake_word.py`) должен накопить ПОЛНОЕ окно `WAKE_WORD_WINDOW_S` (1.5с по умолчанию), прежде чем
    вообще попытаться распознать слово — то есть к моменту срабатывания ключевое слово (и всё сказанное в тот
    же момент) уже физически лежит в этом буфере. Раньше в Gemini уходил только тот 50мс-кусочек аудио,
    который «в моменте» подавался на вход при срабатывании — а не то, что реально распознал Whisper, поэтому
    сам запрос посетителя («оформите визит») локально распознавался, но до модели не доходил, и Gemini слышал
    только хвост фразы или тишину. Исправлено: при срабатывании `app/session_hub.py`'s

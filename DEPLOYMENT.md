# Инструкция по деплою, запуску и настройке

Практическое руководство для того, кто устанавливает и обслуживает систему на роботах R1 и G1. За архитектурой
и объяснением инженерных решений — в `README.md`; здесь только процедуры.

Система разворачивается как **два независимых деплоя одного и того же кода** — один на роботе R1, один на
роботе G1. Они не пересекаются: у каждого свой рабочий каталог, свой `.env`, свой systemd-юнит, свой журнал
данных. Ничего в этой инструкции не подразумевает, что оба деплоя работают на одной машине, но если это
когда-нибудь понадобится (например, для тестового стенда) — разделение уже это допускает, см. раздел 6.

## 1. Требования

- Робот Unitree R1 или G1 с уже установленным вендорским ПО (Unitree SDK, DDS-инфраструктура).
- Python 3.12+ и [uv](https://docs.astral.sh/uv/) на роботе.
- Ключ Google AI Studio с доступом к Gemini Live API.
- Сетевой доступ у робота (Wi-Fi или Ethernet) — см. раздел 7.
- Для реального звука/камеры через аппаратуру робота: собранный `unitree_sdk2py` и рабочая CycloneDDS-сборка
  под iceoryx (обычно уже готовы на роботе — см. раздел 12, если звук падает сегфолтом).
- Для R1: отдельный ПК видеостены с запущенным Factories.exe и wall-агентом (`app/wall`, разворачивается
  отдельно на этом ПК, Windows).

## 2. Установка

Рабочий каталог для каждого профиля — свой, чтобы деплои R1 и G1 не пересекались (см. раздел 6):

```bash
# на роботе R1:
git clone <repo-url> ~/realtimevoice-r1 && cd ~/realtimevoice-r1
# на роботе G1:
git clone <repo-url> ~/realtimevoice-g1 && cd ~/realtimevoice-g1
```

Установка зависимостей — **на роботе всегда с `--inexact`**:

```bash
uv sync --inexact
```

`--inexact` обязателен на роботе: обычный `uv sync` подчищает всё, что не объявлено в `pyproject.toml`, а
`unitree_sdk2py`/`cyclonedds`/`numpy`/`opencv-python` и подобные пакеты вендорского SDK на роботе установлены
вручную, в обход этого файла — обычный `sync` их снесёт.

## 3. Настройка профиля — R1 или G1

| | R1 (презентатор) | G1 (пост охраны) |
|---|---|---|
| Шаблон `.env` | `.env.r1.example` | `.env.g1.example` |
| Обязательно заполнить | `GEMINI_API_KEY`, `WALL_AGENT_URL` | `GEMINI_API_KEY` |
| Справочные данные | `knowledge/*.md` (проекты для презентации) | `config/guard-kb.yaml`, `knowledge_guard/*.md` |
| Systemd-юнит | `deploy/realtimevoice-r1.service` | `deploy/realtimevoice-g1.service` |

```bash
cp .env.r1.example .env   # на роботе R1 — или .env.g1.example на роботе G1
```

Откройте `.env` и заполните отмеченные поля — комментарии в файле объясняют каждую переменную. Профиль
(`ROBOT_PROFILE`) дополнительно и авторитетно фиксируется в systemd-юните (раздел 6) — даже если `.env`
скопирован по ошибке не тот, юнит всё равно запустит нужный профиль.

**Справочные данные — обязательно заменить перед вводом в эксплуатацию.** `config/guard-kb.yaml` и
`knowledge_guard/*.md` (G1), `knowledge/*.md` (R1) в репозитории — примеры, показывающие структуру данных, а
не реальный справочник заказчика. Робот отвечает посетителям **только** тем, что в этих файлах — пустой или
примерный файл означает, что на вопросы вне пары примеров робот честно ответит «не знаю» и предложит обратиться
к сотруднику, а не придумает ответ. Замените их содержимое на реальные данные заказчика (структура и формат —
см. комментарии в `config/guard-kb.yaml` и `app/guard_kb.py`).

## 4. Сборка веб-интерфейса

Веб-интерфейс — статический React-бандл, который FastAPI раздаёт сам. **Собирать нужно там, где есть Node/npm**
(обычно не на самом роботе) и разворачивать только результат сборки — каталог `web/`:

```bash
cd web-src && npm install && npm run build   # пишет прямо в ../web
```

Скопируйте получившийся `web/` в рабочий каталог робота (`rsync`/`scp`) вместе с остальным кодом.

## 5. Проверка вручную (без автозапуска)

Прежде чем настраивать автозапуск, стоит один раз запустить вручную и убедиться, что всё работает:

```bash
cd ~/realtimevoice-r1   # или ~/realtimevoice-g1
export LD_LIBRARY_PATH=~/cyclonedds_ws/install/cyclonedds/lib:$LD_LIBRARY_PATH
export CYCLONEDDS_URI=~/cyclonedds_ws/cyclonedds.xml
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Два экспорта выше нужны, только если в `.env` включено `AUDIO_OUTPUT=robot` или `AUDIO_INPUT=robot` /
`PRESENCE_ENABLED=true` (реальный микрофон/динамик/камера робота — все используют DDS). Если весь звук идёт
через браузер (`AUDIO_OUTPUT=browser`, значение по умолчанию), они не нужны.

Откройте `http://<адрес-робота>:8000` в браузере — должна открыться страница, а голосовой диалог — заработать.
`Ctrl+C` останавливает процесс.

## 6. Автозапуск при включении робота

Используется **пользовательский** systemd (`~/.config/systemd/user/`, не `/etc/systemd/system/`) — это
намеренный выбор: не требует root/sudo вообще, в отличие от системного systemd. Единственное, что нужно
один раз — включить linger, чтобы пользовательские сервисы переживали выход из SSH-сессии и переживали
перезагрузку:

```bash
# на каждом роботе, под тем пользователем, от которого будет работать сервис:
loginctl enable-linger $(whoami)

mkdir -p ~/.config/systemd/user
cp deploy/realtimevoice-r1.service ~/.config/systemd/user/   # на роботе R1
# cp deploy/realtimevoice-g1.service ~/.config/systemd/user/  — на роботе G1

systemctl --user daemon-reload
systemctl --user enable --now realtimevoice-r1.service        # или realtimevoice-g1.service
```

Юниты уже содержат нужные `LD_LIBRARY_PATH`/`CYCLONEDDS_URI`, `Environment=ROBOT_PROFILE=...` и
`Restart=on-failure` — если процесс упадёт или зависнет, systemd поднимет его заново сам, без ручного
вмешательства. Подробности по управлению — раздел 11.

**Если R1 и G1 разворачиваются на одном хосте** (например, тестовый стенд, а не два разных робота): юниты уже
изолированы по рабочему каталогу и профилю, останется только развести порт — поменяйте `--port 8000` на
`--port 8001` в одном из двух `.service`-файлов (в строке `ExecStart=`) и учитывайте это при обращении к API.

## 7. Wi-Fi

Требование — уверенное автоматическое переподключение при потере связи. На NetworkManager (типичная настройка
робота на Ubuntu) это делается один раз при первом подключении к сети:

```bash
nmcli connection modify "<SSID сети>" connection.autoconnect yes connection.autoconnect-retries -1
```

`autoconnect-retries -1` — бесконечные повторные попытки подключения, а не одна-две. Проверить текущее
состояние: `nmcli -t -f NAME,AUTOCONNECT,AUTOCONNECT-PRIORITY connection show`.

**Рекомендуется** дополнительно отключить энергосбережение Wi-Fi-адаптера — известная причина периодических
просадок/подвисаний связи под постоянной нагрузкой (голосовой стриминг работает непрерывно, пока включён
микрофон):

```bash
echo -e "[connection]\nwifi.powersave = 2" | sudo tee /etc/NetworkManager/conf.d/local-wifi-powersave-off.conf
sudo systemctl restart NetworkManager   # SSH-сессия может на секунду оборваться и переподключиться сама
```

Требует sudo. Сам профиль сети/пароль эта команда не трогает — риска потерять сохранённые сети нет.

## 8. Безопасность — токен доступа

По умолчанию (`ACCESS_TOKEN` пусто) веб-интерфейс и API открыты без авторизации — подходит только для
изолированной сети без посторонних устройств. Для любого развёртывания в сети, к которой может подключиться
кто-то посторонний (Wi-Fi гостей, публичная зона), обязательно задать токен:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(24))"
```

Впишите результат в `ACCESS_TOKEN=` в `.env` этого робота (у R1 и G1 — разные токены) и перезапустите сервис.

**Что токен защищает, а что нет**: он закрывает веб-интерфейс целиком — сайт-наблюдатель/пульт оператора
(`/wall`, `/guard`), панель транскрипта, WebSocket `/ws/session` (управление активной сессией: текст, вкл/выкл
микрофона, «Замолчи»). Голосового взаимодействия с самим роботом (микрофон/динамик у стойки) это не касается —
оно не идёт через веб-интерфейс, посетитель у робота токен не вводит и не должен.

**Как использовать на стороне пользователя**: открыть сайт робота в браузере → внизу справа появится окно
«Токен доступа» (или кнопка «Войти», если окно уже закрывали) → вставить токен → сохранить. Токен сохраняется
в `localStorage` этого браузера и подставляется автоматически при каждом обращении — вводить заново не нужно,
пока не очистить данные сайта. На **каждом** устройстве, с которого заходят на сайт, токен нужно ввести один
раз отдельно.

## 9. Проверка работоспособности

Быстрая проверка после установки или обновления:

```bash
curl http://<адрес-робота>:8000/api/profile        # {"profile":"r1"} или {"profile":"g1"}
```

Затем в браузере: открыть сайт, нажать **Start mic**, сказать что-нибудь — статус должен перейти
`listening → speaking`, должен идти звук ответа. Спросить «который час?» — в логе должен появиться вызов
инструмента `get_current_time`, а озвученный ответ — содержать корректное время. Заговорить во время ответа
(barge-in) — воспроизведение должно оборваться быстро. Нажать «Замолчи» — воспроизведение должно остановиться
мгновенно.

Для G1 дополнительно: сказать «оформите визит» → ответить на вопрос о языке → пройти все 6 полей → подтвердить
«да» — карточка должна появиться на `/guard` и записаться в `data/visits.jsonl`.

Для R1 дополнительно: на странице `/wall` нажать кнопку раздела — статус должен показать «На связи» (нужен
запущенный wall-агент на ПК видеостены), в журнале команд — `accepted`.

Полный чек-лист (все 28 пунктов, включая языковые сценарии, безопасность, автозапуск) — в `README.md`,
раздел «Ручной чек-лист».

## 10. Обновление

```bash
cd ~/realtimevoice-r1   # или ~/realtimevoice-g1
git pull                # или rsync новых файлов
uv sync --inexact
cd web-src && npm run build && cd ..   # только если менялся фронтенд
systemctl --user restart realtimevoice-r1.service   # или realtimevoice-g1.service
```

## 11. Управление сервисом

```bash
systemctl --user start   realtimevoice-r1.service    # запустить сейчас
systemctl --user stop    realtimevoice-r1.service    # остановить (не перезапустится сам)
systemctl --user restart realtimevoice-r1.service    # перезапустить (подхватить новый код)
systemctl --user status  realtimevoice-r1.service    # текущее состояние + последние строки лога
journalctl --user -u realtimevoice-r1.service -f     # живые логи (Ctrl+C — выйти)

systemctl --user disable realtimevoice-r1.service    # отключить автозапуск при загрузке (не трогает текущий запуск)
systemctl --user enable  realtimevoice-r1.service    # включить обратно
```

`enable`/`disable` — про то, стартует ли сервис САМ при следующей загрузке робота. `start`/`stop` — про то,
работает ли он ПРЯМО СЕЙЧАС. Это независимые переключатели.

## 12. Диагностика типовых проблем

**Звук/камера падают сегфолтом при `AUDIO_OUTPUT=robot`/`AUDIO_INPUT=robot`/`PRESENCE_ENABLED=true`.**
Почти всегда — несовпадение сборок CycloneDDS: на роботе их обычно две (вендорская в `/usr/local` и отдельная
сборка под `~/cyclonedds_ws`, собранная специально под python-пакет `cyclonedds`), и процесс должен явно
загрузить именно вторую:

```bash
export LD_LIBRARY_PATH=~/cyclonedds_ws/install/cyclonedds/lib:$LD_LIBRARY_PATH
export CYCLONEDDS_URI=~/cyclonedds_ws/cyclonedds.xml
```

Оба варианта уже прописаны в systemd-юнитах — если сегфолт всё равно происходит при запуске через systemd,
проверьте `systemctl --user cat realtimevoice-r1.service`, что переменные не были случайно затёрты. Не
полагайтесь на `.bashrc` — там обычно прописан путь под остальную робо-платформу (`/usr/local`), а не под
`cyclonedds_ws`, и `.bashrc` в любом случае не подхватывается неинтерактивными SSH-командами.

**Процесс не отвечает на `systemctl stop`/обычный `kill`, нужен `kill -9`.** Иногда случается при зависании
внутри блокирующего DDS/вендорского вызова в фоновом потоке, который не реагирует на SIGTERM вовремя. Юниты
уже настроены на это (`TimeoutStopSec=10`, после которого systemd эскалирует до SIGKILL сам) — специально
ничего делать не нужно, кроме как подождать. `Restart=on-failure` поднимет процесс заново автоматически.

**SSH-команда, запускающая сервис в фоне (`nohup ... &`), зависает и не возвращает управление.** Не проблема
самого сервиса — классическая особенность `ssh`+`nohup`: фоновый процесс остаётся привязан к сессии/tty, пока
явно не отвязан. Используйте `setsid` перед командой (`setsid nohup uv run uvicorn ... &`) или, что надёжнее,
управляйте сервисом через systemd (раздел 11) — тогда эта проблема не возникает вовсе.

**В логе часто мелькают `gemini.connection_state state=connecting/connected`.** Это нормально и ожидаемо —
Gemini Live закрывает простаивающие или долго живущие сессии сам, backend переподключается автоматически
(`app/gemini_live.py`). Если рядом видно `detail=proactive session refresh` на уровне INFO — это плановое
обновление сессии (см. `MAX_SESSION_DURATION_S` в `.env`), не ошибка. Тревожиться стоит только если рядом
идут `WARNING`-записи с другим текстом или ответы реально перестали приходить.

**Сайт открывается, но робот не реагирует голосом.** Проверить: (1) в `.env` — `AUDIO_INPUT`/`AUDIO_OUTPUT`
выставлены в `robot`, если ожидается работа через аппаратный микрофон/динамик; (2) микрофон робота включён —
глобальный переключатель (см. раздел «Профили» в README) может быть выключен другим оператором; (3)
`curl http://<робот>:8000/api/profile` вообще отвечает — если нет, сервис не запущен (раздел 11).
